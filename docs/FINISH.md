## 서버 (Cloudflare Workers, 배포됨)

`https://etavia.picpal.workers.dev` — 키를 가리고 응답을 검증해 넘기는 얇은 프록시.
경로 계산·시간 판정은 앱에 남는다.

| 엔드포인트 | 역할 |
|---|---|
| `/extract` | LLM 경유지 추출. 앱 토큰 + 기기당 분당 10회. **앱에는 아직 배선 안 함**(의도적 — LLM 토큰 절약) |
| `/route` | 카카오모빌리티 자동차 길찾기. 경유지 ≤ 5, 미래운행(`departAt`) |
| `/enrich` | 후보 보강 — 네이버 블로그 + 구글 Places |

- `src/schema.ts` — **인젝션의 실제 방어선.** LLM이 무엇을 뱉든 이 스키마를 통과해야 앱에 닿는다
- KV 두 개 생성·배선 완료 (`RATE`, `CACHE`)
- 앱 `.env`에 `SERVER_URL`·`APP_TOKEN`·`KAKAO_REST_KEY` 들어감

**쿼터** — 카카오 자동차 길찾기 일 10,000건 무료(초과 8원/건), 미래운행 일 5,000건.
계획당 5~9회니 하루 1,000건 남짓 무료.

## 채팅 추출

**모델은 `gpt-5.6-sol`로 결정.** 여러 모델 비교는 하지 않기로 했다 — ChatGPT 계정은
설정된 모델만 허용해서 `gpt-5.3-codex`·`gpt-5.1` 모두 400이었다.
`server/src/index.ts`의 `DEFAULT_MODEL`, `OPENAI_MODEL` secret으로 덮을 수 있다.

**전체 147건 실측 기준선 (2026-09-10)**

| | 통과 | 실패 | 미검증 | 무응답 |
|---|---|---|---|---|
| 로컬 목 | 128 | 17 | 2 | — |
| gpt-5.6-sol | **133** | 12 | 2 | **0** |

101K 토큰(40건씩 4배치). `node server/run-llm.mjs`로 재현.

## 최적 경로 계산

설계 `docs/최적경로-설계.md` (2026-09-11, Codex 두 라운드 검토).

- **행렬 API는 없다.** 카카오 다중목적지·Matrix는 제휴 승인 대상, Google Matrix는 요소당 과금.
  실측은 "직행 1 + 전체 경로 R회"뿐이고 응답의 section별 시간을 **재사용**해 나머지 조합을 재채점한다.
- V=1은 상위 8개 실측(9회), V≥2는 R=4 + 조건부 2라운드. 합계 5~8회.
- **추정으로 후보를 삭제하지 않는다.** 추정치는 하한이 아니다.
- 3안 다양성은 실측 후 Jaccard 패널티로.

**구현** — `src/lib/routePlan/`(plan·corridor·enumerate·legs·score·select·mockProvider),
`src/lib/corridorSearch.ts`, Workers `/route`, `serverRouteProvider`. UI 연결까지 완료.

**단일 경유지 seed budget을 8로 제한**(`SINGLE_R`). 예전엔 후보 30개를 전부 측정해
계획당 최대 31회 호출이 나가 서버 분당 한도 40을 넘길 수 있었다.

## 트렌드 후보 추천 (2026-09-12 ~ 09-13)

설계 `docs/superpowers/specs/2026-09-11-trend-candidates-design.md`.
업종 검색일 때 후보 30곳에 네이버 블로그 최근 언급·구글 평점을 붙이고 경로 적합도와 합쳐 추천한다.

**점수** — 경로 적합도 0.4 · 평점 품질 0.35 · 최근 언급 0.25. 축은 슬롯 단위로 켜지거나 꺼지고,
켜지면 미관측 후보는 그 슬롯 관측값의 중앙값으로 채운다.

**실측으로 확인** — 연남동 콜드에서 6곳 중 4곳에 블로그 신호, 그중 제니스커피가 90일 48건.
시뮬레이터에서 추천 탭이 뜨고 1위 카드에 구글 평점이 붙는 것까지 확인.

### 2026-09-13 예산·부분결과 수정 (계획 `docs/superpowers/plans/2026-09-13-enrich-budget.md`)

보강이 매번 빈 결과로 떨어지던 것을 고쳤다. 서버 6.25초 vs 앱 타임아웃 2.5초였다.

| 고친 것 | 왜 |
|---|---|
| 없는 점수 축을 후보별 재정규화 → **관측 중앙값**으로 채움 | 미조회 후보의 점수가 fit 그대로가 돼서, 측정 안 한 가게가 4.0★ 가게를 이겼다 |
| buzz 폐기 규칙 분모를 후보 전체 → **조회분**으로 | 일부만 묻게 되면 미조회를 '언급 0'으로 세어 축이 잘못 꺼진다 |
| buzz 기준을 비율 → **관측 개수 3곳**으로 | 6곳만 묻는데 80%를 걸면 전국 브랜드 두 곳에 축이 꺼진다 |
| `/enrich`에 **`budgetMs` + 부분 결과** | 전부 끝나야 응답해서, 타임아웃을 올려도 콜드는 전부 아니면 전무였다 |
| 블로그 조회 **6곳**(앞 4 + 뒤에서 고르게 2) | 아래 실측 |
| 앱 예산을 **파이프라인 잔여 시간에서 계산** | 고정 8초는 슬롯 3개면 24초. 12초 예산을 넘겨 계획 자체가 실패 |

**실측 지연 (배포된 Worker, 콜드)**

| | 시간 |
|---|---|
| 네이버 블로그 1곳 | 1.7초 |
| 6곳 | 1.7초 |
| 12곳 | 3.4초 |
| `/route` 1회 | 3.1초 |

동시 연결 한도가 6이라 7곳부터 회차가 나뉜다. **6곳이 한 회차에 들어가는 최대치다.**
처음엔 "30곳이라 6.25초"라고 봤는데 실제로는 **호출당 1.7초**였다.

**설계상 알아둘 것**

- 네이버 블로그 검색어는 카카오 장소 이름 정확히 그대로다. 행정동을 붙이면 언급 수가 20배 떨어진다
  (블로거는 "서교동"이 아니라 "홍대"라고 쓴다). 총합 20,000 초과는 전국 집계로 보고 폐기한다.
- 블로그를 부르기 전엔 인기를 모르므로 "인기 상위 N곳"은 원리적으로 불가능하다.
  앞 4곳 + 뒤에서 고르게 2곳은 가까운 순 쏠림을 막는 탐색용 타협이지 인기 보장이 아니다.
- 업종에 따라 신호가 거의 안 붙는다. 은행·ATM은 30곳 중 구글 1곳·블로그 0곳이었다 — 정상이다.
- 홍대 mock catalogue는 `.env`에 실제 카카오 키가 있으면 닿을 수 없다(실제 검색이 우선).
- 구글이 로마자 이름만 주는 매장은 `normalizeName`이 스크립트 변환을 안 하므로 60m 단독 매칭
  규칙(`placeMatch.ts` 규칙 4)에만 기댄다 — 그 반경에 후보가 둘 이상이면 평점이 안 붙는다.

`npx tsc --noEmit -p .`는 서버 파일을 0개 검사한다.

npm test

Paste. `simctl` 타이핑은 ASCII만 통과한다.

## 행동 로그 (2026-09-13)

계획 `docs/superpowers/plans/2026-09-13-behaviour-log.md`.

전에는 주행 중(`tracker.tsx`)만 기록돼서, 계획을 만드는 행동은 하나도 안 남았다.
09-13 시뮬레이터에서 계획을 처음부터 끝까지 만들었는데 로그 파일 자체가 안 생겼다.

**이벤트 두 종을 더했다**

| 종류 | 내용 |
|---|---|
| `act` | 사용자 행동. `a` 가 `plan.start` 같은 점 표기라 grep 으로 갈래를 자른다 |
| `net` | 바깥 호출 한 번 — 엔드포인트·지연·성공 여부·붙은 신호 수 |

모든 줄에 `r`(runId)이 붙는다. 하루에 계획을 두 번 세워도 어느 줄이 어느 계획
소속인지 갈린다. `--run <id>` 로 하나만 볼 수 있다.

**리듀서가 아니라 dispatch 를 감쌌다.** 리듀서는 순수해야 하고 StrictMode 가 개발 중
두 번 부르므로 안에서 로그를 남기면 줄이 두 배가 된다. 액션은 전부 미들웨어를 지나므로
화면이 늘어도 로그가 빠지지 않는다 — `src/state/actionLog.ts` 가 액션을 한 줄로 옮긴다.

**id 대신 이름을 싣는다.** 예전 `{"k":"notify","id":"s-1"}` 은 어느 가게인지 알려면
위쪽 `plan` 줄과 대조해야 했다.

**소음을 줄였다.** `fix` 는 15m 이동 또는 30초 경과일 때만, `geofence` 는 판정이
바뀌는 순간과 30초 heartbeat 만. 09-12 로그는 39줄 중 30줄(77%)이 이 둘이었다.

**net 계측은 공급자를 감싸서 한다.** `serverProvider`·`enrichClient` 안에서 부르면
node 테스트가 `expo-file-system` 에서 죽는다. `planFlowProvider.tsx` 가 유일한 이음매다.

**실측 확인** — 시뮬레이터에서 목적지 → 채팅 → 칩 삭제 → 경로 찾기 → 후보 교체 →
확정 → 추적 시작까지 하고 로그만으로 전부 재구성됐다. 그 자리에서 실제 결함도
드러났다(업종 슬롯 2개면 보강이 빈다 — `NEXT.md` 맨 위).

**타임라인 스크립트**도 같이 고쳤다 — `act`·`net` 렌더, `events` 없는 row 에서 죽던 것,
`--run <id>` 필터.

```bash
node scripts/tracklog-timeline.mjs track-export.jsonl [--run <id>]
```

**채팅 원문을 남긴다.** 추출을 다듬으려면 사용자가 실제로 뭐라고 쳤는지가 제일 값지다.
기기 로컬 전용이고 사용자가 개발 메뉴에서 직접 내보낼 때만 나간다.

## 보강 예산 분배 수정 (2026-09-13)

행동 로그를 넣자마자 드러난 결함이다.

```
이전  NET /enrich 2522ms  budgetMs=2500 · results=0  · blog=0 · google=0
      NET /enrich 2507ms  budgetMs=2500 · results=0  · blog=0 · google=0
이후  NET /enrich 4425ms  budgetMs=5000 · results=30 · blog=2 · google=8
```

업종 슬롯 2개에 예산 5초를 **미리 반으로 나눠** 각 2.5초를 줬는데, 네이버 호출
하나가 1.7초라 서버가 어느 슬롯에서도 한 건을 못 끝냈다. 둘 다 빈 결과였다.

**굴러가는 마감으로 바꿨다.** 슬롯마다 '그 시점에 남은 예산 전부'를 준다.
캐시가 더워 빨리 끝나면 다음 슬롯이 나머지를 쓰고, 콜드라 다 쓰면 다음 슬롯은
건너뛴다 — 결과가 버려질 호출에 쿼터를 쓰지 않는다. 전부 비느니 앞 슬롯 하나라도
붙는 게 낫다. 나눠 주는 방식으로는 '더우면 둘 다'가 불가능했다.

| 상수 | 전 | 후 | 근거 |
|---|---|---|---|
| `ENRICH_MIN_SLOT_MS` | 0.8초 | 4.4초 | 서버가 구글 몫 1.8초를 떼고 블로그에 1.9초는 줘야 1회차가 끝난다 → 서버 예산 3.7초 + 여유 0.7초 |
| `SERVER_MARGIN_MS` | 0.3초 | 0.7초 | 실측 서버 오버헤드가 0.3초보다 커서, 서버가 만든 부분 결과를 클라이언트가 버리고 있었다 |
