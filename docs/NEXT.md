### near 는 위치까지만 잡는다 — 결혼식 케이스는 아직 반쪽이다

2026-09-17 에 `near` 축(`src/lib/nearSide.ts`)을 넣었다. 잡는 것: 사용자가 말한 위치
("회사 근처 카페"), 그리고 대중교통에서 들고 못 타는 품목("커피 사서"). 못 잡는 것:

- **머무는 경유지.** "결혼식 가는데 근처 카페 들렀다 갈게"는 위치도 시간도 못 잡는다.
  `dwellFor`(`src/state/runPlan.ts:66`)가 **검색어**만 보고 `why` 를 안 봐서 "커피 사기"와
  "결혼식 전에 기다리기"가 똑같이 5분이다. 12시 약속에 11시 도착이면 55분이 비는데
  앱은 5분짜리 경유지를 넣고 "50분 일찍 도착"이라고 말한다.
- 고치려면 `ScoreContext`(`src/lib/routePlan/score.ts:10`)에 `arriveBy` 가 들어가야 한다.
  지금 거기엔 위치도 마감도 없다. 채점 구조를 건드리는 일이라 별도 단계다.
- 원리: **도착 시각이 고정돼 있고 여유가 남으면 그 여유는 마지막에 쓰는 게 안전하다.**
  앞에서 쓰면 이후 이동 전부가 지연 리스크로 남고, 뒤에서 쓰면 이미 도착해 있으니 0이다.

같이 볼 것:
- **`CARRY` 표가 `queries` 까지 읽어 넓게 문다**(`src/lib/nearSide.ts`). `[why, ...queries]` 를 한 문자열로
  이어 검사하므로 **검색어에 '커피'가 들어가기만 해도** 물성 신호가 선다. 실측한 오작동:
  `queries:['커피숍'] + why:'친구 만나기'`(앉아 있을 카페인데 목적지 쪽으로 한정), `why:'커피 마시기'`,
  `why:'원두 커피 사기'`(원두는 들고 탈 수 있다), `why:'꽃게 사기'`(`꽃` 에 걸린다).
  이때 후보가 남으면 완화가 안 돌아 **화면에 아무 표시 없이** 후보가 뒤쪽 40% 로 좁혀지고 교체 시트에도
  출발지 쪽이 안 뜬다. 고칠 때 후보: `why` 만 읽기, 또는 구매 동사와 함께 보기. 단순히 `why` 만 읽게 하면
  `queries:['꽃집'] + why:''` 를 잃으므로 테스트를 먼저 손봐야 한다.
- **`NEAR_SPLIT_S = 0.6` 은 비율이라 경로 길이에 따라 뜻이 달라진다**(`src/lib/nearSide.ts`).
  30km 주행에서 "집 앞 편의점"은 **앞쪽 12km 전부**를 통과시킨다 — s=0.39·우회 0분인 가게가
  s=0.02·우회 2분인 진짜 집 앞 가게를 이겨서 제약이 사실상 안 듣는다. 반대로 짧은 대중교통에서는
  앵커 검색 반경이 1.5km(`corridorSearch.ts`)라 총 5km 경로의 하차역 뒤쪽 후보가 s≈0.6 언저리로 떨어지고,
  마지막 도보가 총거리의 40% 를 넘으면 하차역 자체도 0.6 미만이다 — 완화가 자주 돈다.
  하차 앵커(`AnchorKind === 'alight'`)로 자르는 쪽이 대중교통에서는 더 정확할 수 있다.
- **목(`src/lib/intent.ts`)은 한 문장의 위치를 모든 경유지에 똑같이 붙인다.**
  `"집 앞 편의점 들렀다가 회사 근처 카페 가자"` → 편의점까지 `end` 가 된다. `내려서` 도
  `"짐 내려서 갈게"` 에 걸린다. 서버가 죽었을 때만 도는 경로라 급하지는 않지만, 경유지별 판정이 맞다.
- **`count ≥ 2` 의 근본 원인은 이 축 밖에 있다.** `enumerate.ts` 의 중복 방지는 "후보가 1곳뿐인 count=2"
  에서도 빈 계획을 낸다 — `near` 는 그 상태에 닿기 쉽게 만들 뿐이다. `applyNear` 의 `need` 는 near 가
  만드는 경로만 막는다. 검색 자체가 1곳만 찾은 경우는 여전히 빈 계획이 된다.
- `server/run-cases.mjs` 는 `src/lib/intent.ts` **하나만** `tsc --outDir /tmp/etavia-intent` 로 떨궈
  flat 경로 `${OUT}/intent.js` 를 import 한다(`rootDir` 미지정). 그래서 `intent.ts` 에 **로컬 import 를
  하나라도 넣으면 러너가 깨진다** — tsc 프로그램에 파일이 늘어 rootDir 추론이 `src` 로 바뀌고 출력이
  `${OUT}/lib/intent.js` 로 밀린다. 이 전제는 코드 어디에도 적혀 있지 않다(2026-09-17 에 한 번 밟았다).
  게다가 실패한 뒤 `/tmp/etavia-intent` 에 옛 결과가 남아 **조용히 틀린 숫자**를 낸다 — 다시 돌리기 전에
  `rm -rf /tmp/etavia-intent`. 고치려면 `--rootDir src` 를 주고 import 경로를 `${OUT}/lib/intent.js` 로.

### `far` 는 성공이 아니다 (2026-09-16 최종 리뷰가 미룬 것)

검색어 폴백을 붙이면서 드러난 것이다. `corridorSearch.ts` 는 `far` 를 **"상한까지 0건 —
더 멀리 한 번만 보고 가장 가까운 3곳"** 이라고 스스로 정의해 놓았는데, 호출부 두 곳이
그걸 성공으로 읽는다. 이번에 그중 하나를 새로 추가했다 — `runPlan.ts` 의 폴백 조건
`if (found.candidates.length > 0) break;`.

**증상**: `'샌드위치 파는 카페'` 라는 *이름의* 가게가 경로에서 한참 떨어진 곳에 하나 있으면,
경로 바로 옆 멀쩡한 '카페' 는 검색조차 되지 않는다. 카카오 키워드 검색은 부분 매칭이라
**0건이 아니라 엉뚱한 1건**을 주는 쪽이 흔하다. 경유지가 빠지는 것보다 나쁠 수 있다 —
빠지면 화면이 말이라도 해 주지만(`OptionsScreen.tsx` 의 "못 찾아 뺐어요"), 이건 말없이
경로를 망가뜨린다.

**왜 이번에 안 했나**: 제대로 고치려면 "약한 결과를 더 나쁜 것으로 덮어쓰지 않는다" 는
의미론을 새로 정해야 한다(`far` 1건 → 폴백 `none` 0건이면 있던 후보까지 잃는다).
그건 `searchStatus` 등급 간 우선순위를 정하는 설계 판단이라 자기 몫의 검토가 필요하다.

**같이 볼 것**:
- `src/lib/intentClient.ts` — `prefers` 가 필수 타입인데 `looksLikeIntent` 가 안 본다.
  구버전 워커가 떠 있으면 런타임 `undefined` 인데 타입은 `string[]` 이라 거짓말이다.
  지금은 아무도 안 읽어서 무해하다.
- `prefers` 를 랭킹에 실제로 쓰는 일 — `PlaceCandidate` 에 `category_name` 이 없어
  (`places.ts` 가 카카오 응답에서 버린다) 배선이 필요하고, `IntentChip` 도 손대야 한다.
  카카오엔 메뉴 데이터가 없어 "샌드위치를 파는 카페" 를 아는 방법이 사실상 없다는 것도
  같이 봐야 한다 — 모르는 걸 아는 척 거르지 않는 게 이 저장소 원칙이다.
- `runPlan.ts` 의 예산 임계값 `timeoutMs * 0.5` — 실측으로 조정할 값이다.
  첫 검색이 오래 걸리면 폴백이 한 번도 안 돌 수 있다.
- 후보 상한 `slice(0, 3)` 에 전용 회귀 테스트가 없다.

## 보강(/enrich) 이월

**큰 것부터.**

- **30곳을 다 덮으려면 클라이언트 팬아웃.** 지역+업종 질의는 스파이크로 기각됐다
  (위 '바로 다음' 참고). 호출마다 별도 Worker 인보케이션이라 6곳씩 병렬로 부르면
  연결 6개 벽을 우회한다 — 실측 30곳 동시 3.4초.
- **블로그 캐시 stale 재사용.** 지금은 24시간이 지나면 미조회 취급이다. fresh 24시간 /
  stale 14일로 나눠 stale 값은 순위에 쓰고 백그라운드로 갱신하면 콜드가 거의 사라진다.
  설계 §2.1.1의 "24시간을 넘기지 않는다"를 바꾸는 일이라 **사양 수정이 먼저다**.
- **플래너 예약 3.5초는 측정값이 아니라 근사다.** `/route` 1회가 3.1초인 걸로 잡았다.
  플래너 실측 p95를 재서 `PLANNER_RESERVE_MS`(`src/state/runPlan.ts`)를 교체해야 한다.
  이 값이 보강 예산을 직접 깎으므로 과대하면 보강이 굶고 과소하면 계획이 타임아웃된다.
- **예산 카운터를 Durable Object로.** KV는 read-modify-write가 원자적이지 않고 읽기가
  eventual consistency다. 실측에서 카운터가 64→56으로 되돌아가는 걸 봤다(옛 값을 읽고 덮어씀).
  앱이 슬롯을 순차로 불러도 다른 사용자의 동시 요청까지는 못 막는다.
  **Durable Object로 옮기기 전까지 슬롯 병렬화는 금지다.**
- **`/enrich-batch`로 슬롯 통합.** 슬롯마다 따로 부르니 슬롯 수만큼 지연이 쌓인다.
  한 요청에 모든 슬롯을 담으면 캐시 조회·예산 예약·외부 호출을 한 번에 묶는다.
  Durable Object 예산 게이트가 선행 조건이다.
- **파이프라인 데드라인이 터져도 보강 루프는 취소되지 않는다.** `race()`가 결과를 계획에
  반영하지 않을 뿐, 진행 중이던 `/enrich`와 남은 슬롯 호출은 계획이 FAIL로 끝난 뒤에도
  백그라운드로 나간다(회랑 검색·플래너도 마찬가지). **타임아웃난 계획도 구글 예산을 쓴다.**
- **비동기 보강은 이번 계획의 품질을 못 올린다.** 다음 요청용 캐시 예열일 뿐이고,
  확정된 경유지가 뒤늦게 바뀌는 race·UI 튐이 생긴다. 하려면 planId·inputHash로 늦은 결과를
  막고, 자동 교체 대신 '더 인기 있는 대안 발견' 제안으로만 써야 한다.

**운영**

- **구글 일일 할당량 40을 유료 전환 직후 반드시 건다.** 무료 체험판이라 콘솔의 "할당량 수정"이
  비활성이다. 기본값이 75,000/일이다. 그전까지는 `/enrich`의 월 900회 카운터가 유일한 방어선이다.
- 구글 `hours`(영업시간)는 받아만 두고 영업 상태 판정에 배선하지 않았다. 배선하려면
  `runPlan`의 자동 스왑도 같이 고쳐야 한다 — `runPlan`은 후보를 고를 때 시트의 `isSelectable`
  (마감 필터)을 적용하지 않으므로, hours만 붙이고 필터링을 빼먹으면 자동 스왑이 마감 매장을 고를 수 있다.
- 네이버 HUB 유료 전환 공지가 뜨면 단가를 확인하고 재검토한다.

- 경유지에 **"할 일 추가" 입구가 없다.** 새 계획 흐름으로 만든 경유지는 할 일이 비어 있어 A6의
  "할 일 N/M" 칩이 안 뜨고, 할일 시트는 딥링크(`etavia://timeline?sheet=task`)로만 열린다.
- 죽은 표면 정리 — `legTable`, `applyOption`·`selectOption`·`setOptionStore`·`stopsForOption`.
- `applyChat`이 인식 실패 메시지에도 `reset`을 부른다.

## 미해결로 남긴 것

- `화장실 급해` — 되묻을지 바로 추출할지 미정. Codex는 바로 추출했고 그쪽이 나을 수 있다
- `내일 아침 9시까지` — 스키마에 날짜가 없다
- `올리브영 들르고 어 아니 그 뭐냐 빵집` — Codex가 말더듬을 취소로 읽어 올리브영을 버렸다
- **비결정성이 실측됐다.** `구시까지 도착`이 36건 테스트에선 09:00, 147건에선 null. 같은 입력에 다른 답이다.
  **`temperature=0`은 애초에 적용된 적이 없다** — 이 모델은 기본값(1)만 받고, 0을 실으면 400을 낸다
  (2026-09-15 실측: `'temperature' does not support 0 with this model`). 그래서 지금은 보내지 않는다.
  **실질 방어는 칩 UI** — 사용자가 뭘 알아들었는지 보고 고칠 수 있으면 비결정성이 치명상이 되지 않는다.
- `endpoints`를 4건 전부 놓쳤다. 스키마엔 있는데 프롬프트가 시키지 못했다. 예시 3개를 박아 넣었고
  **재실행으로 확인해야 한다** (`node server/run-llm.mjs`).
- 집·회사 좌표가 여의나루역·신정네거리역 임시값 (`src/data/mockData.ts`)
- 개발 메뉴의 **`도착 안 해도 혼잡도 묻기`가 켜져 있다.** 실사용 전에 꺼야 한다

## 음성 입력 — 실기기에서만 확인되는 것

시뮬레이터는 마이크가 없고 `kTCCServiceSpeechRecognition` 을 **미리 허용**해 둔다
(2026-09-20 TCC.db 확인: 모든 서비스 `auth_value=2`). 그래서 음성 인식 권한 대화상자는
시뮬레이터에서 영영 뜨지 않는다 — 앱 문제가 아니다. TestFlight 빌드
(`npm run release -- <버전>`, 태그가 트리거)로 확인한다. EAS 가 prebuild 하므로
서명·Xcode 패치는 손댈 게 없다.

- [ ] 계획 화면 → 마이크 탭 → 권한 **두 번**(마이크·음성 인식) 한국어 문구
      (마이크 쪽은 2026-09-20 시뮬레이터에서 확인됨, 음성 인식 쪽만 미확인)
- [ ] "스타벅스 들러서 가자" → 글자가 차오르고, 말을 멈춘 뒤 2~3초 안에 입력창에 채워진다
- [ ] 이어서 "약국도" → 공백 하나로 붙는다
- [ ] 듣는 중 재탭 → 그때까지 글자로 끝난다
- [ ] 기내 모드 → 온디바이스 재시도가 되거나(iOS 17+ ko-KR), 안 되면 `인터넷이 없어…` 자리표시
- [ ] 설정에서 마이크 끄기 → 마이크 탭 → `설정에서…` 자리표시 → 재탭 → 설정 앱이 열린다
      (자리표시 표시까지는 시뮬레이터에서 확인됨. `Linking.openSettings()` 는 미확인)
- [ ] 브랜드명 오인식(올리브용 등)은 전송 후 LLM 이 교정하는지 — STT 쪽 수정 금지

**자리표시가 입력창 폭에서 잘린다** — `설정에서 마이크·음성 인식을 켜 …` 로 끝난다.
한 줄 안에 들어가는 더 짧은 문구로 줄이거나 두 줄을 허용할지 정해야 한다.

**`expo install`·`npm install` 은 Xcode 26 패치를 되돌린다**(`SWIFT_RETURNS_RETAINED` 2건 부활).
로컬 시뮬레이터·실기기 빌드 전에 매번 확인한다. `patch-package` 로 고정하는 게 맞다.
