# /enrich 예산·부분결과 수정 계획

**Goal:** 보강이 실제로 앱에 도달하게 만든다. 지금은 서버가 6.25초, 앱 타임아웃이 2.5초라 매번 빈 결과다.

**Spec:** docs/superpowers/specs/2026-09-11-trend-candidates-design.md

## 측정된 사실

| 경우 | 시간 |
|---|---|
| 30곳 콜드 | 6.25초 |
| 12곳 콜드 | 4.03초 |
| 30곳 웜 | 1.31초 |
| 앱 타임아웃 | 2.5초 |

Cloudflare Workers는 요청당 동시 바깥 연결이 6개다. 블로그 30건은 병렬이어도 5회차로
나뉜다. 위 수치가 이 계산과 맞는다 — 호출 수를 줄이는 것 말고 콜드를 단축할 방법이 없다.

## Global Constraints

- `npm test` 와 `npx tsc --noEmit -p .` 와 `npx tsc --noEmit -p server` 셋 다 통과해야 한다.
- 슬롯 보강은 순차를 유지한다. 병렬로 되돌리면 KV 예산 카운터가 슬롯 수만큼 샌다.
- 서버는 앱 코드를 import 하지 않는다(`enrichTypes.ts` 는 `types.ts` 의 사본).
- 부분 실패는 실패가 아니다. 블로그만 와도 200 이다.

### Task 1: 점수 — 없는 축을 중립값으로 채운다

지금 `blend()` 는 축이 빠지면 남은 가중치로 다시 나눈다. 그래서 미조회 후보의 없는
축이 "나머지 축과 같은 값"으로 imputation 된다. 경로적합 0.5 · 구글 3.5★(품질 0.2)인
후보는 0.43, 경로적합 0.5 · 구글 미조회인 후보는 0.50 이다. **측정 안 한 가게가
측정해서 낮게 나온 가게를 이긴다.** 지금도 30곳 중 20곳이 구글 미조회라 살아있는 결함이다.

축은 슬롯 단위로 켜지거나 꺼진다:
- 그 슬롯에서 한 후보라도 관측됐으면 축을 켜고, 미관측 후보는 **관측값의 중앙값**으로 채운다
- 아무도 관측 못 했으면 축을 통째로 끄고 **모든 후보에 대해 똑같이** 재정규화한다

후보마다 따로 재정규화하지 않는다.

**Files:** `src/lib/trendScore.ts`, `src/lib/trendScore.test.ts`

- [ ] 실패 테스트: 구글 3.5★ 후보가 같은 경로적합의 미조회 후보보다 앞선다
- [ ] 실패 테스트: 아무도 구글 신호가 없으면 순위가 경로적합 순과 같다
- [ ] 중앙값 imputation 구현
- [ ] 테스트 통과 확인 · 커밋

### Task 2: 점수 — buzz 폐기 규칙을 커버리지 기준으로

`blogQueried` 를 신호에 추가한다. 조회했는데 신호가 없는 경우(전국 브랜드)와
아예 안 물어본 경우를 구분하기 위해서다.

```
queried  = blogQueried 인 후보
observed = 그중 blog 가 있는 후보
coverage = observed / queried
zeroRate = observed 중 weighted === 0 의 비율
buzz 축 ON = observed > 0 && coverage >= 0.8 && zeroRate < 0.8
```

**Files:** `src/lib/enrich/types.ts`, `server/src/enrichTypes.ts`, `src/lib/trendScore.ts`, `src/lib/trendScore.test.ts`

- [ ] 실패 테스트: 조회 12곳 중 10곳이 언급 0 → buzz 축이 꺼진다

### Task 3: 서버 — 블로그를 12곳으로 줄인다

30곳 전부 묻지 않는다. 입력 순서(회랑 거리순) 기준으로:
- 앞에서 8곳
- 나머지에서 고르게 4곳

가까운 순 쏠림을 막으려고 고르게 4곳을 섞는다. 블로그를 부르기 전엔 인기를 모르므로
"인기 상위 12곳"은 원리적으로 불가능하다 — 이건 탐색용 타협이지 인기 보장이 아니다.

**Files:** `server/src/enrich.ts`, `server/src/enrich.test.ts`

### Task 4: 서버 — 예산 시간과 부분 결과

요청에 `budgetMs` 를 받는다. 내부 마감에서 끝난 것만 반환한다. 지금은 30곳이 전부
끝나야 응답하므로 타임아웃을 얼마로 올리든 콜드에선 전부 아니면 전무다.

- `budgetMs` 없으면 8000. 500~8000 으로 자른다.
- 블로그 단계에 60%, 구글 단계에 40% 를 준다. 구글이 굶지 않게 하려는 것 —
  지금 구조는 블로그가 전부 끝난 뒤에야 구글로 넘어간다.
- 개별 호출을 각 단계 마감과 race 시킨다. 마감을 넘긴 호출은 `null` 로 떨어지고
  그 후보만 신호가 없다.
- 예산 카운터는 호출 **전에** 예약하므로 마감에 걸려 못 쓴 몫이 카운터에 남는다.
  기존 정정 단계가 실제 지출로 내려쓴다(조건부 쓰기).

**Files:** `server/src/enrichSchema.ts`, `server/src/enrich.ts`, `server/src/enrich.test.ts`

- [ ] 실패 테스트: `budgetMs: 1000` · 느린 블로그 목 → 1.2초 안에 응답, 결과는 부분
- [ ] 실패 테스트: `budgetMs` 없으면 기존처럼 전부 기다린다
- [ ] 실패 테스트: 마감에 걸려도 200 이고 `budget` 필드가 온다
- [ ] 구현 · 테스트 통과 · 커밋

### Task 5: 앱 — 파이프라인 잔여 시간에서 예산을 계산한다

고정 2.5초를 버린다. 슬롯 3개면 8초 고정은 24초라 12초 예산을 넘긴다.

```
남은시간  = deadline - now
보강예산  = clamp(남은시간 - 3500(플래너 예약) - 500(여유), 0, 5000)
슬롯당    = 보강예산 / 슬롯수
슬롯당 < 800 이면 보강을 건너뛴다
```

3500 은 플래너 라우팅(최대 9회) 예약이다. p95 를 재서 교체해야 한다 — NEXT.md 에 적는다.

`EnrichFn` 이 `timeoutMs` 를 받도록 바꾸고, 클라이언트가 `budgetMs` 를 몸체에 실어 보낸다.
서버 마감이 클라이언트 abort 보다 먼저 오도록 `budgetMs = timeoutMs - 300` 으로 준다.

**Files:** `src/lib/enrich/enrichClient.ts`, `src/lib/enrich/mockEnrich.ts`, `src/state/runPlan.ts`, 각 테스트

- [ ] 실패 테스트: 남은 시간이 모자라면 보강을 아예 건너뛴다
- [ ] 실패 테스트: 슬롯 순차 호출이 유지된다(동시 호출 없음)
