# 검색어에서 조건 떼어내기 — 구현 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** LLM이 `"샌드위치 파는 카페"` 같은 구(句)를 검색어로 내놓아도 경유지가 경로에서 사라지지 않게 한다.

**Architecture:** 조건을 검색어에서 떼어내되, 원천(LLM)만 믿지 않는다. 세 겹으로 간다 —
(1) 구가 아는 업종어로 끝나면 업종어만 남긴 후보를 **덧붙이고**(`expandQueries`),
(2) 첫 검색어가 0건이면 **다음 후보로 넘어가며**(`runPlan` 폴백),
(3) 프롬프트·스키마가 조건을 `prefers`로 **분리**한다. 1·2가 앱 쪽 방어선이고 3이 원천 교정이다.

**Tech Stack:** TypeScript · node:test(`tsx --test`) · Expo SDK 57 · Cloudflare Workers(`server/`)

**Spec:** 이 문서의 「배경」 절. 별도 스펙 파일 없음 — 2026-09-16 조사에서 근거를 전부 실측했다.

## 배경 — 실측된 원인 사슬

```
LLM  queries: ["샌드위치 파는 카페"]        ← 후보 1개, 조건이 섞인 구
  ↓
planRequest.ts:24   query: c.queries[0]      ← 폴백 배열이 여기서 잘린다
  ↓
placeQuery.ts       카페 행엔 query 재정의가 없다 → 구를 그대로 카카오로
  ↓
카카오 키워드 검색   상호명 매칭이라 그런 가게가 없음 → 0건
  ↓
runPlan → Slot      candidates: [] · searchStatus: 'none'
  ↓
enumerate.ts:24     slots.filter(s => s.candidates.length > 0) → 경로에서 빠진다
```

codex 실측(gpt-5.6-sol, `server/llm-results-phrasequery.json`):

| 입력 | 모델이 낸 검색어 |
|---|---|
| 카페 들릴껀데 샌드위치 팔면 좋겠다 | `[샌드위치 파는 카페]` |
| 조용한 카페에서 잠깐 일하다 갈게 | `[조용한 카페]` |
| 샌드위치 팔면서 조용한 카페 있을까 | `[샌드위치 파는 조용한 카페]` |
| 편의점 들렸다가 커피랑 샌드위치 사서 | `[편의점]` ✅ |

**후보를 하나만 낸다.** 그래서 폴백 배선(2)만으로는 안 되고 정규화(1)가 함께 있어야 한다.

**Interfaces:**

**규칙** — 질의 `q`마다:
1. 공백을 지운 문자열로 TABLE 행을 찾는다(`planSearch`와 같은 방식).
2. 행이 없으면 아무것도 안 한다.
3. `q === hit.term`이면 이미 업종어다 — 안 한다.
4. **`q.includes(hit.term)`이 아니면 안 한다.** ← 이게 브랜드를 지키는 조건이다. `'메가커피'`는 `'카페'`를 품지 않으므로 `'카페'`로 뭉개지지 않는다.
5. 통과하면 `hit.term`을 뒤에 덧붙인다. 원래 질의는 **지우지 않는다** — 첫 시도는 여전히 사용자가 말한 그대로다.
6. 중복 제거(순서 보존).

- [ ] **Step 3: TABLE 각 행에 `term`을 박는다**

`TABLE`의 타입 선언에 `term: string;`을 추가하고(필수 필드), 각 행에 아래 값을 넣는다. **기존 `re`·`query`·`pathAny`·`code`·`local`은 한 글자도 건드리지 않는다.**

| 행(`re`로 식별) | `term` |
|---|---|
| `편의점\|씨유\|…` | `'편의점'` |
| `대형\s*마트\|대형\s*슈퍼` | `'대형마트'` |
| `(?:^\|[^스])마트$\|…` | `'마트'` |
| `^빵$\|빵집\|베이커리(?!카페)\|제과점` | `'빵집'` |
| `카페\|커피` | `'카페'` |
| `정육\|고기\s*사` | `'정육점'` |
| `문구` | `'문구'` |
| `꽃집\|꽃\s*사\|플라워` | `'꽃집'` |
| `세탁소\|빨래방\|코인빨래` | `'세탁소'` |
| `서점\|책방` | `'서점'` |
| `약국` | `'약국'` |

대형마트 행의 `term`이 `'마트'`가 아니라 `'대형마트'`인 이유: `'대형마트'` 질의가 자기 자신으로 확장되는 걸 막는다(규칙 3). 그 행은 이미 `query: '마트'`로 검색어를 바꾸므로 폴백이 필요 없다.

- [ ] **Step 4: `expandQueries`를 구현한다**

`placeQuery.ts` 맨 끝에 추가:

```typescript
/**
 * 검색어 후보를 넓힌다 — `'샌드위치 파는 카페'` → `['샌드위치 파는 카페', '카페']`.
 *
 * LLM이 조건을 검색어에 섞어 내놓는 걸 앱에서 받아내는 자리다(실측 2026-09-16:
 * gpt-5.6-sol 이 `[샌드위치 파는 카페]` 하나만 낸다). 카카오 키워드 검색은
 * **상호명 매칭**이라 그런 이름의 가게가 없어 0건이 되고, 0건이면 경유지가
 * 경로에서 빠진다.
 *
 * 원래 질의를 지우지 않고 **뒤에 덧붙이기만** 한다 — 첫 시도는 사용자가 말한
 * 그대로여야 하고, 업종어는 그게 0건일 때만 쓰는 그물이다.
 *
 * `q.includes(term)` 조건이 브랜드를 지킨다. '메가커피'는 카페 행에 걸리지만
 * '카페'를 품지 않으므로 확장하지 않는다 — 붙였다면 브랜드가 0건일 때 엉뚱한
 * 카페로 조용히 갈아탔을 것이다.
 */
export function expandQueries(queries: string[]): string[] {
  const out: string[] = [];
  const push = (q: string) => { if (q && !out.includes(q)) out.push(q); };

  for (const raw of queries) {
    const q = raw.trim();
    push(q);
    const hit = TABLE.find(t => t.re.test(q.replace(/\s+/g, '')));
    if (!hit) continue;
    if (q === hit.term) continue;
    if (!q.includes(hit.term)) continue;
    push(hit.term);
  }
  return out;
}
```

```typescript

        const target = Math.max(st.count, KC);

        const runSearch = async (query: string) => {
          const corridor = () => searchAlong(
            poly, query,
            { need, target, initialRadiusM: initialRadiusM(request.mode), maxRadiusM: maxRadiusM(request.mode, slack, rho) },
            search,
          );
          // 앵커가 있으면 역 주변부터. 한 곳도 없으면 오늘 나오던 후보까지 잃지 않게 회랑으로 떨어진다

            ? await searchAtAnchors(anchors, query, {
                need, target,
                maxRadiusM: Math.min(ANCHOR_MAX_M, maxRadiusM(request.mode, slack, rho)),
              }, search)
            : await corridor();
          if (anchors.length > 0 && r.status === 'none') {
            // 앵커에서 0건이라 회랑으로 다시 찾는다. 호출 수는 더한다 —
            // 이 숫자는 실제로 나간 장소 검색 요청 수를 감사하려고 남기는 것이라
            // 앞의 앵커 조회를 빼고 적으면 로그가 사용량을 축소해서 말한다
            const anchorCalls = r.calls;
            const viaCorridor = await corridor();
            r = { ...viaCorridor, calls: viaCorridor.calls + anchorCalls };
          }
          return r;
        };

        // 검색어 폴백 — LLM이 조건을 섞은 구를 내놓아도(실측: `샌드위치 파는 카페`)
        // 업종어 후보로 넘어가 경유지를 살린다. 호출 수는 모든 시도를 합산한다.
        const queries = st.queries.length > 0 ? st.queries : [''];
        let used = queries[0];
        let found = await runSearch(used);
        let calls = found.calls;
        for (const next of queries.slice(1)) {
          if (found.candidates.length > 0) break;
          const retry = await runSearch(next);
          calls += retry.calls;
          used = next;
          found = retry;
        }
        found = { ...found, calls };
        // 전부 0건이면 사용자가 말한 그대로를 보여 준다 —
        // "…는 경로 근처에서 못 찾아 뺐어요"(OptionsScreen)에 찍히는 값이다
        if (found.candidates.length === 0) used = queries[0];

        return {
          // 자동차면 주차 없음 제외·가능 우선 — 아는 정보만 거른다(실제 검색은 아직 주차를 모른다)
          id: st.id, query: used, stopKind: st.stopKind, why: st.why,
          candidates: applyParkingPolicy(found.candidates, request.mode).slice(0, MAX_CANDIDATES), dwellMin: dwellFor(used),
          count: Math.max(1, st.count), flexible: st.flexible, openNow: st.openNow, searchStatus: found.status,
          searchRadiusM: found.radiusM, searchCalls: found.calls,
        } satisfies Slot;
```
