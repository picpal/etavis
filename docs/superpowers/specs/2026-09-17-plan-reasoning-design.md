# 동선의 이유를 말하는 앱 — 설계 v3

> 2026-09-17 작성 · 2026-09-18 v3 · 상태: 설계 확정, 구현 전
>
> v1·v2 는 codex 리뷰에서 각각 P1 4건·7건으로 반려됐다. 둘 다 **플래너의 계약을
> 안 읽고 그 위에 덧붙이려 한** 게 원인이었다. v3 는 덧붙이지 않고 **점수를 바꾼다.**
> 무엇이 틀렸는지는 「앞선 판이 틀린 지점」에 남긴다.

## 무엇을 만드나

**경로 화면 상단에 두 개의 토글을 둔다.**

```
┌──────────────┬──────────────┐
│  편한 순서    │   최단 시간   │
└──────────────┴──────────────┘
   약국 → 마트 → 집        52분
   장 본 걸 들고 약국에 들어가지 않아도 돼요
```

- **최단 시간** — 지금과 같다. 총 소요시간이 가장 짧은 안.
- **편한 순서** — 짐을 진 채 이동하는 시간을 비용으로 친 안.

둘이 같은 안이면 **토글을 숨긴다.** 눌러도 안 바뀌는 버튼은 신뢰를 깎는다.

설명 한 줄은 `편한 순서` 쪽에만 붙고, LLM 이 쓴다.

## 왜

| 증상 | 사용자가 모르는 것 |
|---|---|
| 집에 가는데 `마트 → 약국 → 집` 이 나온다 | 순서는 시간만 보고 정해진다. 장바구니는 점수에 없다 |
| 더 빠른 매장을 놔두고 다른 곳을 고른다 | 인기 때문에 최대 10분까지 손해를 감수한다 (`runPlan.ts:31`) |
| 재계산하면 고른 장소가 바뀐다 | `RESULT` 가 `overrides` 를 비운다 (`planFlow.ts:121`) |

뿌리는 하나다. **앱이 의도를 갖고 고르는데 그 의도를 한마디도 안 한다.** 토글은 그 의도에 이름을 붙이는 일이다.

## 앞선 판이 틀린 지점

| 무엇 | 코드의 사실 |

| v1 "3곳까지 전수라 항상 나온다" | 실측 시드는 **4개**(`plan.ts:19`), 최종 옵션은 `finalMeasured` 에서만 고른다 |
| v1 "`/enrich` 처럼 나중에 채운다" | `/enrich` 는 **플래너 앞**에서 12초 예산 안에 끝난다(`runPlan.ts:242`→`:298`) |
| v1 "`selectedOptionIdx` 만 옮긴다" | 그게 경로·도착시각·지도를 전부 바꾼다. 2.5초 뒤 화면 점프다 |
| v2 "1단계만으로 순서가 고쳐진다" | `pickOptions` 는 최단안을 0번에 두고(`select.ts:72`) `RESULT` 가 0번을 고른다(`planFlow.ts:115`). **옵션에 넣는 것과 고르는 것은 다르다** |
| v2 "시드에 자동 반영된다" | `pickSeeds` 는 `estC` 로 고르는데(`select.ts:37`) `estC` 는 거리 추정일 뿐 짐을 모른다(`plan.ts:90-95`) |
| v2 "시드를 하나 예약한다" | 대중교통은 계획 1건이 **10콜**이고 V=2 에서 이미 8~9콜을 쓴다(`transitBudget.ts`). 늘릴 자리가 없다 |

## 1. 짐 시간을 잰다

`scorePlan` 은 이미 **구간별 분**을 낸다(`score.ts:68` `legsMin`). 구간은 `[출발→v0, v0→v1, …, vN→도착]` 이라 방문 `i` 이후 이동은 `legsMin.slice(i+1)` 이다.

```
burdenMin(plan) =
  Σ  방문 i 의 슬롯이 loadAfter === 'hard'  →  sum(legsMin.slice(i + 1))
  +  방문 i 의 슬롯이 loadBefore === 'hard' →  sum(legsMin.slice(0, i + 1))
```

- **`mode === 'car'` 면 0.** 트렁크가 있으면 짐이 부담이 아니다. `decideNear` 가 차를 일찍 빼는 것과 같은 이유다(`nearSide.ts:57`).
- 짐이 여럿이면 더해진다. 겹치는 구간이 두 번 세지는 건 맞다 — 두 개를 들고 있다.
- **`count > 1` 슬롯도 자연히 처리된다.** 구간 합이라 같은 슬롯의 방문이 몇 개든 각자의 위치에서 계산된다. 순서 목록으로 표현하려던 v2 가 못 하던 것이다.

`scorePlan` 이 슬롯 태그를 봐야 하므로 `ScoreContext` 에 `tagsOf(slotId) → StopTags` 를 더한다. `Scored` 에 `burdenMin` 이 붙는다.

### 가중치

```
comfortMin = totalMin + W · burdenMin        W = 1.5
```

**"짐을 든 1분을 이동 1.5분으로 친다."** 임의의 상수가 아니라 제품 문장이고, 테스트로 고정한다. `mode === 'car'` 면 `burdenMin` 이 0 이라 `comfortMin === totalMin` 이다.

`totalMin` 은 **건드리지 않는다.** 화면에 보이는 숫자는 계속 진짜 소요시간이다. `comfortMin` 은 순위에만 쓴다.

## 2. 시드 — 늘리지 않고 기준만 바꾼다

`pickSeeds` 는 지금 `byC[0]`·`byC[1]`·`byA[0]`·`byB[0]` 을 고른다(`select.ts:36-52`). 첫 자리만 바꾼다.

| | 지금 | v3 |
|---|---|---|
| 1 | `byC[0]` 거리 추정 최선 | **`byComfort[0]`** — `estC + W·burdenMin` 최선 |
| 2 | `byC[1]` | **`byC[0]`** — 순수 최선 (그대로 남긴다) |
| 3 | `byA[0]` | `byA[0]` |
| 4 | `byB[0]` | `byB[0]` |

- **호출 수가 안 는다.** `R = 4` 그대로다. 대중교통 예산도 그대로다.
- **두 토글 모두 실측된 안을 갖는다** — 1번이 `편한 순서`, 2번이 `최단 시간` 후보다.
- 짐이 없으면 `byComfort === byC` 라 `planKey` 중복으로 걸러지고 **지금과 똑같이 동작한다**(`select.ts:44`).
- 잃는 것: `byC[1]`(2순위 거리 추정). 다양성 축 `byA`·`byB` 는 남는다.

추정 단계에서도 `scorePlan` 이 `legsMin` 을 낸다 — 측정된 구간이 없으면 추정으로 채운다(`score.ts:61-66`). 그래서 실측 전에도 `burdenMin` 을 계산할 수 있다.

## 3. 옵션 — 두 안을 모두 남긴다

`pickOptions(finalMeasured, directMin, 3)` 의 불변식은 **"1안은 최단"** 이다(`select.ts:72`). 깨지 않는다.

```
1. 지금처럼 3개를 고른다 (1안 = 최단, 나머지는 시간+overlap)
2. comfortBest = finalMeasured 중 comfortMin 최소
3. comfortBest 가 3개 안에 없으면 → 마지막 자리를 그것으로 교체
```

- **퇴출 규칙이 명시된다** — 마지막(점수 최하) 하나. v2 가 안 정해 둔 자리다.
- 1안은 여전히 최단이다. `+8분 컷` 도 그대로다 — `comfortBest` 만 컷과 무관하게 들어온다.
- `comfortBest` 가 `+30분` 을 넘으면 넣지 않는다. 그 정도면 편의가 아니라 다른 여행이다.

`PlanResult` 에 `comfortIdx: number | null` 을 더한다. 토글이 볼 값이다.

## 4. 화면

```
┌──────────────┬──────────────┐
│  편한 순서    │   최단 시간   │
└──────────────┴──────────────┘
  장 본 걸 들고 약국에 들어가지 않아도 돼요      ← 한 줄, 작게, 흐리게
  ─────────────────────────────────
  약국 → 마트 → 집        52분
```

### 토글 밑 한 줄

버튼만으로는 두 기준이 무슨 뜻인지 모른다. 바로 밑에 **한 줄**을 둔다.

| 선택 | 문구 |
|---|---|
| 최단 시간 | `총 이동 시간이 가장 짧아요` — 고정 문구, 코드가 쓴다 |
| 편한 순서 | LLM 의 `why`. **없으면** `짐을 들고 이동하는 시간을 줄였어요` |

고정 문구가 **기준 설명이자 빈 상태**를 겸한다. LLM 이 도착하면 그 자리를 케이스별 문장으로 갈아끼운다.

방해되지 않게:

- **한 줄 높이를 미리 잡는다.** 설명이 나중에 와도 아래가 안 밀린다. 줄이 생기며 레이아웃이 움직이면 그것 자체가 "말없이 바뀐다"다.
- 본문보다 작고 흐리게. 읽고 싶으면 읽고, 아니면 눈이 지나간다.
- 60자 상한이라 두 줄로 안 넘어간다. 넘으면 자른다.
- 토글이 숨겨지면 이 줄도 같이 숨는다.

### 토글을 숨기는 조건

`comfortIdx` 가 `null` 이거나 `0` 이면 **토글을 숨긴다.** 보여줄 차이가 없다.

토글은 `selectedOptionIdx` 를 `0` ↔ `comfortIdx` 로 옮긴다. 둘 다 `options` 배열의 실제 항목이므로 `overrides` 가 `optionIdx` 로 키를 잡는 것과 충돌하지 않는다(`planFlow.ts:133`).

**기본 선택은 `0`(최단 시간)이다.** 지금 동작을 안 바꾼다. 사용자가 `편한 순서` 를 눌러야 바뀐다 — 말없이 바뀌는 일이 없다.

## 5. 설명 — `/reason`

여기서만 LLM 을 쓴다. **고르지 않는다. 설명만 한다.**

### 어디서 도나

새 서버 엔드포인트 `/reason`. `server/src/index.ts` 의 known path 목록과 라우팅 분기에 **명시적으로** 추가한다 — 빠뜨리면 마지막 분기가 `/extract` 처리라 엉뚱한 프롬프트로 흘러간다(`index.ts:127,166`).

### 언제 부르나

`comfortIdx !== null` 일 때만, `RESULT` 와 트렌드 스왑이 **둘 다 끝난 뒤**(`runPlan.ts:312` 이후) 한 번. 순서를 못 박는다 — v2 는 이걸 안 정해 뒀다.

### 입력 — `parseReasonRequest` (`schema.ts`)

| 필드 | 검증 |
|---|---|
| `text` | 문자열, 500자로 자름 |
| `mode` | `car`·`transit`·`walk` enum |
| `fast` | `{ stops: string[], totalMin: number }` |
| `comfort` | 같은 모양 |
| `stops` | 최대 6개, 각 40자 |
| `totalMin` | 유한, `0 < n < 1440` |
| 본문 원시 크기 | **8KB 초과 거부 — `req.json()` 전에** (`index.ts:87` 이 먼저 읽는다) |

옵션 목록도 인덱스도 안 보낸다. **두 안과 문장만** 준다. 고를 게 없으니 인덱스를 주고받을 이유가 없다.

`timingSource` 가 추정인 계획은 안 보낸다(`types.ts:168`은 결과 단위 필드라, `Scored.unknownLegs > 0` 으로 계획 단위로 판정한다).

### 출력 — `parseReasonResponse`

```json
{ "why": "장 본 걸 들고 약국에 들어가지 않아도 돼요" }
```

| 검증 | 실패하면 |
|---|---|
| 문자열, 공백 제거 후 비어 있지 않음 | **설명 없음** |
| 개행·제어문자 없음 | 제거 |
| 60자 | 자름 |
| **숫자·시간·거리·속도 주장이 없음** | **설명 없음** (아래) |

### 사실 주장을 어떻게 막나

codex 가 정확히 짚었다 — 숫자만 막으면 `"두 배 더 걸려요"`, `"훨씬 빠른 길이에요"`, `"문 닫기 전에 갈 수 있어요"` 가 다 통과한다. 전부 코드가 검증 못 하는 주장이다.

그래서 **금지어 목록이 아니라 프롬프트와 검증을 같이 좁힌다:**

- 프롬프트가 요구하는 것은 **"왜 이 순서가 편한가"** 한 가지다. 빠르기·거리·영업시간은 묻지 않는다.
- 검증은 숫자(아라비아·한글 수사), 시간·거리·속도 단위, 비교급 어휘(`빠르`, `가까`, `늦`, `일찍`, `오래`)를 거른다. 걸리면 **설명을 안 낸다.**
- 설명이 없어도 토글과 `+12분` 은 그대로 뜬다. **설명은 장식이지 기능이 아니다.**

`reasonCode` enum 으로 구조화하자는 제안은 받지 않는다 — 규칙 어휘를 다시 관리하는 길이고, 정형화 안 된 상황을 못 담는다. 대신 **말할 수 있는 범위를 좁히고, 벗어나면 버린다.**

### 늦게 온 설명

설명은 `selectedOptionIdx` 를 **안 바꾼다.** 그래서 v2 의 "선택 강탈" 문제가 없다. 그래도 엉뚱한 계획에 붙으면 안 되므로 두 값을 확인한다.

| 값 | 무엇 |
|---|---|
| `planRunId` | `START` 에서 정해 상태에 저장. 모든 비동기 액션이 이 값을 싣고, 리듀서가 **다르면 버린다** |
| `comfortKey` | 요청 당시 `comfortBest` 의 `planKey`(`select.ts:10`). 달라졌으면 버린다 |

`planRunId` 는 `RESULT` 뿐 아니라 `SLOTS`·`FAIL`·`SET_REASON` 전부에 건다. 지금은 어떤 액션에도 실행 식별자가 없어, 겹친 `runPlan` 의 옛 결과가 새 상태에 들어올 수 있다.

### guard

`PER_MIN` · `PER_MIN_IP` · `PER_DAY` **세 표 모두**에 `/reason` 을 넣는다. `PER_DAY` 에 없으면 `overDailyCap` 이 `cap === undefined` 로 **그냥 통과시킨다**(`guard.ts:124`).

**`/extract` 상한은 줄이지 않는다.** v2 는 1200→900 으로 쪼개려 했는데, 그건 비용 분할이 아니라 핵심 기능 25% 감축이다 — 901번째 추출이 429 를 받고 로컬 목으로 떨어진다.

`/reason` 은 **일 200** 으로 따로 연다. 근거: `comfortIdx !== null` 일 때만, 계획당 한 번만 부른다. 실기기 로그상 계획 대부분이 V=1~2 이고 짐 태그가 붙는 건 일부다. 200 을 넘으면 설명이 안 붙을 뿐 경로는 나온다.

## 6. 검증

| 단계 | 무엇 | 비용 |
|---|---|---|
| 1 | 단위 테스트 — `burdenMin` 계산, 시드 1번 자리 교체, 옵션 퇴출 규칙, 토글 숨김 조건, 입출력 파서, `planRunId` 불일치 폐기 | 0 |
| 2 | 목 기준선 — `node server/run-cases.mjs` | 0 |
| 3 | **codex** 로 설명 프롬프트를 다듬는다 | 0 (구독) |
| 4 | **앱 API 실측** — gpt-5.6-terra 반복 | 과금 |

codex 는 codex 모델이라 terra 가 아니다. 3단계는 "프롬프트가 말이 되는가"를 공짜로 거르는 자리다.

### 무엇이 결정적이고 무엇이 아닌가

**정직하게 적는다.** v2 는 "1단계는 결정적"이라 써놓고 그 입력인 태그가 흔들린다고 같은 문서에 적었다. 모순이었다.

| | 결정적인가 |
|---|---|
| `burdenMin` 계산·시드·옵션·토글 | **예** — 같은 태그를 넣으면 같은 답 |
| `loadBefore`/`loadAfter` 태그 | **아니다** — 추출 LLM 이 만든다 |
| 설명 문구 | **아니다** |

즉 **같은 문장을 두 번 넣으면 토글이 뜰 수도 안 뜰 수도 있다.** 2026-09-17 측정에서 태그는 9케이스 중 7건이 흔들렸다(다만 `decideNear` 는 그중 5건을 분기 순서로 흡수했다).

`burdenMin` 은 그런 흡수가 없다 — `loadAfter` 가 `none` 으로 흔들리면 `burdenMin = 0` 이고 토글이 사라진다.

**대표 케이스 10개 × 5회**를 재고, 토글 출현이 뒤집히는 비율이 **30%** 를 넘으면 태그 프롬프트부터 다시 조인다. 설명 문구는 별도로 **20%** 를 상한으로 본다.

|---|---|
| **주차** | 데이터가 없다. Places 의 `parkingOptions` 로 가져올 수는 있으나 FIELD_MASK·보강 단계·점수 반영이 줄줄이 붙는 별도 축이다 |
| **트렌드 스왑 이유 표시** | 같은 `/reason` 으로 붙일 수 있지만, 먼저 순서부터 맞힌다. 한 번에 둘을 하면 흔들림의 원인을 못 가른다 |
| **사용자 선택 보존** | `overrides` 를 사용자 것과 시스템 것으로 가르는 별도 작업(`runPlan.ts:369` 가 같은 맵에 쓴다) |
| **편집 후 동선 재검토** | `usePlanRequest.ts:26` 이 `order: 'auto'` 를 하드코딩한다 |
| **다중 턴 문맥** | `/reason` 은 마지막 문장만 본다. 전체 대화를 보내면 개인정보 범위가 달라져 별도 결정이 필요하다 |

## 8. 알려진 한계

- **경유지 4곳 이상**은 `enumerate.ts` 가 beam 으로 자른다. 편의 순열이 잘리면 `comfortIdx` 가 `null` 이 되고 토글이 안 뜬다. 실사용은 V=1~2 다.
- **`W = 1.5` 는 측정값이 아니다.** 제품 판단이고, 바꾸려면 테스트를 같이 고친다.
- **`unknownLegs > 0` 인 계획**은 설명을 안 붙인다. 추정 위에서 편의를 말하면 근거가 없다.
- **`/reason` 도 인젝션 표면**이다. 사용자 문장이 들어간다. 출력이 숫자·비교급 없는 60자 문자열이고 실패 시 그냥 안 붙는다. 방어선은 `schema.ts` 다.

## 9. 이 설계가 닫는 것

`마트 → 약국 → 집` 이 **기본값으로는 그대로다.** 대신 `편한 순서` 버튼이 뜨고, 누르면 `약국 → 마트 → 집` 과 그 이유가 보인다.

말없이 바뀌는 것은 하나도 없다. 앱이 두 답을 다 계산했다는 사실 자체가 화면에 보인다 — 그게 이 작업의 요지다.
