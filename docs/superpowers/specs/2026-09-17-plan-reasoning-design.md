# 동선의 이유를 말하는 앱 — 설계

> 2026-09-17 · 상태: 설계 확정, 구현 전

## 무엇을 만드나

계산이 끝난 경로 후보들을 **실제 소요시간과 함께** LLM 에게 보여주고, 사용자 문장에 비춰 **어느 것이 편한지 고르고 한 줄로 설명하게** 한다. 코드는 그 판단을 받아 추천 순서를 정하고 설명을 화면에 띄운다.

한 줄로: **LLM 은 "사람 사정", 코드는 "측정과 계산".**

## 왜 — 세 가지 증상, 하나의 뿌리

시뮬레이터 확인에서 나온 것들이다.

| 증상 | 사용자가 모르는 것 |
|---|---|
| 집에 가는데 `마트 → 약국 → 집` 이 나온다 | 순서는 시간만 보고 정해진다. 장바구니는 점수에 없다 |
| 더 빠른 매장을 놔두고 다른 곳을 고른다 | 인기(트렌드) 때문에 최대 10분까지 손해를 감수한다 (`runPlan.ts:31`) |
| 재계산하면 고른 장소가 바뀐다 | `RESULT` 가 `overrides` 를 비운다 (`planFlow.ts:121`) |

뿌리는 하나다. **앱이 의도를 갖고 고르는데 그 의도를 한마디도 안 한다.** 그래서 잘한 판단도 실수처럼 보이고, 실수는 원인을 알 수 없다.

## 지금 코드가 하는 일

```
enumerate.ts   방문 순열을 전부(V≤3) 만든다
plan.ts:164    pickOptions(finalMeasured, directMin, 3)  →  3개를 고른다
```

**`약국 → 마트` 순서는 이미 계산돼 있다.** 시간순으로 밀려서 안 보일 뿐이다. 순서를 정하는 세 파일(`enumerate.ts` · `plan.ts` · `score.ts`)에 `near` 도 물성 태그도 한 번도 안 나온다 — 순수하게 시간만 본다.

## 구조

```
  사용자 문장 ─→ [추출 LLM] ─→ 장소·조건        (건드리지 않는다)
                                  │
                                  ▼
                            [코드: 검색·실측·순열]
                                  │
                        순서 3개 + 실제 소요시간
                                  │
                                  ▼
                          [판단 LLM] ─→ 번호 하나 + 이유 한 줄
                                  │
                                  ▼
                            [schema 검증] ─→ 화면
```

### 왜 예측이 아니라 판단인가

처음에는 추출 단계에서 LLM 이 경유지 사이 제약(`{earlier, later, why}`)을 미리 뱉게 하려 했다. 버렸다. 두 가지 때문이다.

1. **LLM 이 시간을 모르는 채로 판단한다.** 정작 핵심은 맞바꿈인데("+12분이면 그냥 들고 갈래" vs "+2분이면 당연히") 그 숫자를 못 보고 제약을 낸다.
2. **추출 프롬프트를 건드린다.** 2026-09-17 에 겨우 잡은 대표 34케이스 기준선(29/34)이 흔들린다. v11 에서 `needWhen` 정의 하나 조이는 데 재측정을 두 번 했다.

판단 방식은 둘 다 없앤다. 그리고 AGENTS.md 의 **"LLM은 '무엇을'만 뽑는다 — 소요시간·거리·도착 가능 여부를 만들게 하면 안 된다"** 를 구조적으로 만족한다. LLM 이 시간을 **만들지 않고 받아서 읽는다.**

### 부수 효과: 순환·인덱스 검증이 통째로 사라진다

제약 방식은 순환(A→B→A)과 없는 인덱스를 검사해야 했다. 판단 방식의 출력은 **번호 하나와 문자열 하나**다. 검증이 "0 이상 N 미만인가"로 끝난다.

## 어디서 도나

**새 서버 엔드포인트 `/reason` 이다.** 앱에서 직접 OpenAI 를 부르지 않는다 — 키가 번들에 들어가고, 과금 방어선(`guard.ts` 의 기기·IP·일일 상한)을 못 태운다. `/extract` 와 같은 자리, 같은 규칙이다.

앱 쪽은 `intentClient.ts` 와 같은 모양의 얇은 클라이언트 하나다: 부르고, 실패하면 **판단 없음**으로 떨어진다. 폴백이 목이 아니라 "아무것도 안 함"이라는 점만 다르다.

`guard.ts` 의 세 표에 `/reason` 항목을 더한다 — `PER_MIN` · `PER_MIN_IP` · `PER_DAY`. 셋 중 하나라도 빠지면 그 방어선에 구멍이 난다. 상한을 넘으면 429 → 판단 없음.

값은 `/extract` 기준으로 잡는다(기기당 분당 10 · IP당 30 · 일 1200). `/reason` 은 `/extract` 보다 자주 불릴 수 없다 — 계획을 세워야 부를 수 있고, 계획은 추출 뒤에 온다.

## 입출력

### 판단 LLM 에 보내는 것

```json
{
  "text": "지하철 타고 가는데 마트 들러서 장 보고 약국 갔다 집에 갈게",
  "mode": "transit",
  "options": [
    { "i": 0, "stops": ["이마트 역삼점", "온누리약국"], "totalMin": 40 },
    { "i": 1, "stops": ["온누리약국", "이마트 역삼점"], "totalMin": 52 }
  ]
}
```

**`mode` 를 반드시 넣는다.** 지하철인지 차인지 모르면 편의 판단이 성립하지 않는다 — 차는 트렁크가 있어 짐이 부담이 아니고, 우산은 걸을 때만 급하다. 현재 추출 요청에는 모드가 안 실린다(`intentClient.ts:98`).

장소는 **이름만** 준다. 좌표·거리는 판단에 쓸 일이 없고, 주면 LLM 이 거리를 추론하려 든다.

### 받는 것

```json
{ "pick": 1, "why": "장 본 걸 들고 약국에 들어가지 않아도 돼요" }
```

`why` 는 **표시용 문자열일 뿐 코드가 해석하지 않는다.** 사용자에게 그대로 보인다.

### 검증 — 방어선은 `server/src/schema.ts` 다

프롬프트 규칙은 1차선일 뿐이다(AGENTS.md).

| 검증 | 실패하면 |
|---|---|
| `pick` 이 정수이고 `0 ≤ pick < options.length` | 판단 없음으로 처리 |
| `why` 가 문자열 | 판단 없음으로 처리 |
| `why` 길이 60자 | 자른다 |

**판단이 없으면 지금과 똑같이 동작한다.** 경로는 무조건 나온다. 이건 기능이 아니라 장식이라는 뜻이고, 그게 맞다 — 설명이 없다고 길을 못 찾으면 안 된다.

## 화면

```
1안   40분   빠른 길
2안   52분   짐 안 들고 (+12분)
             장 본 걸 들고 약국에 들어가지 않아도 돼요
```

**옵션 배열은 재정렬하지 않는다.** `selectedOptionIdx` 만 `pick` 으로 옮기고, 그 안에 이유를 붙인다. 순서를 흔들면 사용자가 방금 본 "1안"이 다음 순간 다른 것을 가리킨다 — `overrides` 가 `optionIdx` 로 키를 잡고 있어서(`planFlow.ts:133`) 실제로 엉뚱한 슬롯에 붙는다.

나머지 안도 그대로 보인다 — 사용자가 뒤집을 수 있다. 추천이지 강요가 아니다.

`+12분` 은 **코드가 계산한다.** LLM 이 만든 숫자를 화면에 띄우는 일은 없다.

## 비용과 지연

| | |
|---|---|
| 비용 | 1콜 약 $0.01 (gpt-5.6-terra, 2026-09-17 실측 $10.39/1000콜) |
| 지연 | 중앙 2.5초 · p90 6.3초 |
| 체감 | **0** — 경로를 먼저 그리고 설명만 나중에 채운다 |

`/enrich` 가 이미 그 방식이다(예산 안에서 뒤늦게 채우고, 없으면 그 단계를 건너뛴다).

**안 부르는 경우:** 옵션이 1개거나 경유지가 1곳이면 고를 것이 없다. 호출하지 않는다. 쓸모없을 때 돈이 안 나간다.

## 검증 순서

AGENTS.md 의 사다리를 그대로 탄다. 새 프롬프트이므로 새로 밟아야 한다.

| 단계 | 무엇 | 비용 |
|---|---|---|
| 1 | 단위 테스트 — 검증·폴백·호출 생략 조건 | 0 |
| 2 | **codex** 로 판단 프롬프트를 다듬는다 | 0 (구독) |
| 3 | **앱 API 실측** — gpt-5.6-terra 로 반복 측정 | 과금 |

**codex 는 codex 모델이라 terra 가 아니다.** 2단계는 "프롬프트가 말이 되는가"를 공짜로 거르는 자리고, "terra 가 실제로 그렇게 하는가"는 3단계에서만 나온다.

### 흔들림을 잰다

판단에는 **완충재가 없다.** 물성 태그는 흔들려도 `decideNear` 의 분기 순서가 흡수했다(2026-09-17 측정: 7건 중 5건 흡수, 방향이 바뀐 건 2건). 여기서는 LLM 이 고른 번호가 곧 결과다.

다만 피해가 작다. 최악이 "틀린 순서로 확정"이 아니라 **"이번엔 다른 안을 추천"** 이고, 나머지 안이 그대로 보이며, 확정한 뒤에는 다시 부르지 않는다.

같은 입력을 반복해 **추천이 뒤집히는 비율**을 잰다. 심하면 그때 완충을 고민한다 — 지금 미리 만들면 필요 없는 걸 만든다.

## 범위 밖

| | 왜 |
|---|---|
| **주차** | 데이터가 없다. `/enrich` 는 평점·리뷰수·영업시간만 가져온다. Google Places 의 `parkingOptions` 로 가져올 수는 있으나 FIELD_MASK·보강 단계·점수 반영이 줄줄이 붙는 별도 축이다 |
| **사용자 선택 보존** | `overrides` 를 사용자 것과 시스템 것으로 가르는 별도 작업. 지금은 트렌드 스왑이 같은 맵에 써서(`runPlan.ts:369`) 구분이 불가능하다 |
| **편집 후 동선 재검토** | `usePlanRequest.ts:26` 이 `order: 'auto'` 를 하드코딩한다. 전체 재계산을 붙이면 사용자가 드래그한 순서를 먹는다 — 먼저 `order` 배선부터 고쳐야 한다 |
| **경유지 4곳 이상의 최적 순서** | `enumerate.ts` 가 beam 으로 자른다(V≥4). 편의 순서가 잘려 후보에 없을 수 있다. 3곳까지는 전수 계산이라 항상 나온다 |

## 알려진 한계

- **4곳 이상**은 위와 같이 편의 순서가 후보에 없을 수 있다. 억지로 찾으려 탐색을 늘리면 계산이 느려지고, 4곳 이상 자체가 드물다.
- **판단이 늦게 오면** 사용자가 이미 다음 화면으로 넘어갔을 수 있다. 그때는 버린다 — 지나간 요청의 답을 뒤늦게 반영하면 화면이 저절로 바뀐다. `PlanScreen.tsx:352` 의 `seq` 패턴과 같다.
- **판단 LLM 도 인젝션 표면**이다. 사용자 문장이 들어가기 때문이다. 출력이 번호와 표시 문자열뿐이라 피해 범위가 좁고, 방어선은 `schema.ts` 다.

## 이 단계가 끝나면

`마트 → 약국 → 집` 이 고쳐지고(추천이 바뀌므로), 왜 그런지가 화면에 보인다. 세 증상 중 둘이 같이 닫힌다 — 순서 문제와 설명 문제는 같은 호출로 풀린다.

남는 것은 **사용자 선택 보존**이다. 그건 다음 단계다.
