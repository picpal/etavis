# 동선의 이유를 말하는 앱 — 설계 v2

> 2026-09-17 작성 · 2026-09-18 개정 · 상태: 설계 확정, 구현 전
>
> v1 은 codex 리뷰에서 P1 4건으로 반려됐다. 전부 **코드를 안 읽고 쓴 전제** 때문이었다.
> 무엇이 틀렸는지는 「v1 이 틀린 지점」에 남긴다 — 같은 실수를 반복하지 않기 위해서다.

## 무엇을 만드나

두 가지를 한다.

1. **태그가 후보를 살려둔다** — `loadBefore`/`loadAfter` 로 유도한 "편의 순서"에 실측 시드를 하나 예약하고, 옵션 컷에서 면제한다. 코드만 한다. LLM 없다.
2. **LLM 이 고르고 설명한다** — 살아남은 옵션들을 실제 소요시간과 함께 주고, 사용자 문장에 비춰 어느 것이 편한지 고르고 한 줄로 설명하게 한다.

한 줄로: **태그는 후보를 살리고, LLM 은 판단하고, 코드는 잰다.**

## 왜 — 세 가지 증상, 하나의 뿌리

| 증상 | 사용자가 모르는 것 |
|---|---|
| 집에 가는데 `마트 → 약국 → 집` 이 나온다 | 순서는 시간만 보고 정해진다. 장바구니는 점수에 없다 |
| 더 빠른 매장을 놔두고 다른 곳을 고른다 | 인기 때문에 최대 10분까지 손해를 감수한다 (`runPlan.ts:31`) |
| 재계산하면 고른 장소가 바뀐다 | `RESULT` 가 `overrides` 를 비운다 (`planFlow.ts:121`) |

뿌리는 하나다. **앱이 의도를 갖고 고르는데 그 의도를 한마디도 안 한다.**

## v1 이 틀린 지점

codex 리뷰가 잡았고, 넷 다 코드로 확인했다. 새 설계는 이것들을 전제로 깔고 시작한다.

| v1 이 쓴 것 | 코드의 사실 |
|---|---|
| "`+12분` 짐 안 드는 옵션을 보여준다" | `pickOptions` 가 **최단안 +8분 초과를 버린다**. `deltaMaxMin = min(8, max(2, 0.15·direct))` (`select.ts:66,73`) — 그 옵션은 LLM 에 **도달하지 못한다** |
| "3곳까지 전수 계산이라 항상 나온다" | 순열 열거는 전수지만 **실측 시드는 4개**(`plan.ts:19` `DEFAULT_R = 4`)고, 최종 옵션은 `finalMeasured` 에서만 고른다 |
| "`/enrich` 가 이미 먼저 그리고 채우는 방식이다" | `/enrich` 는 **플래너 앞**에서 같은 12초 예산 안에 끝난다 (`runPlan.ts:242` → `:298`). 그런 구조가 아니다 |
| "`selectedOptionIdx` 만 옮긴다" | 그게 **경로·도착시각·지도·확정버튼을 전부 바꾼다.** 체감 0 이 아니라 2.5초 뒤 화면 점프다 |

그리고 v1 에 아예 없던 것: 실행 식별자, 입력 검증, `/reason` 의 known-path 분기(`guard.ts:124` — `PER_DAY` 에 없는 버킷은 **무제한 통과**한다).

## 1단계 — 태그가 후보를 살린다 (코드만)

### 편의 순서를 정의한다

`decideNear` 와 같은 자리, 같은 모양의 순수 함수를 하나 더 만든다. 방향이 아니라 **순서**를 낸다.

```
comfortOrder(slots, mode) → slotId[] | null
```

- `mode === 'car'` 면 `null`. 트렁크가 있으면 짐이 부담이 아니다. `decideNear` 가 차를 일찍 빼는 것과 같은 이유다.
- `loadAfter === 'hard'` 인 슬롯을 **뒤로**, `loadBefore === 'hard'` 인 슬롯을 **앞으로**.
- 해당 슬롯이 없거나, 정렬해도 기본 순서와 같으면 `null`.

**이것이 순서를 정하지는 않는다.** 실측할 가치가 있는 순열 하나를 지목할 뿐이다. 최종 선택은 여전히 시간과 LLM 판단이 한다. 규칙으로 동선을 확정하는 게 아니다.

### 시드를 하나 예약한다

`pickSeeds(ranked, R)` 는 지금 `byC[0]`·`byC[1]`·`byA[0]`·`byB[0]` 순으로 채운다 (`select.ts:36-52`). 여기에 `comfortOrder` 가 지목한 순열을 **첫 번째로** 넣는다. `R` 은 4 그대로다 — 실측 호출 수가 늘지 않는다.

같은 순열이 이미 뽑혔으면(`planKey` 중복) 아무 일도 일어나지 않는다.

### 옵션 컷을 면제한다

`pickOptions` 는 `+dmax` 초과를 버린다. **편의 시드에서 나온 계획 하나만 면제**하고, 남은 자리를 그것에 준다.

- 면제는 **최대 1개**. 컷의 존재 이유(터무니없는 안을 안 보여준다)를 통째로 없애지 않는다.
- 면제된 옵션에는 `deltaMin` 이 이미 붙어 있다(`PlanOption.deltaMin`). 화면이 `+12분` 을 그대로 쓴다.
- 상한은 둔다: `+30분` 을 넘으면 면제하지 않는다. 그 정도면 편의가 아니라 다른 여행이다.

**여기까지가 1단계다.** LLM 없이도 `마트 → 약국` 이 고쳐진다 — 편의 순서가 옵션에 들어오고, 사용자가 고를 수 있다. 다만 **왜 그게 있는지는 아직 설명되지 않는다.**

## 2단계 — LLM 이 고르고 설명한다

### 어디서 도나

**새 서버 엔드포인트 `/reason`.** 앱에서 직접 OpenAI 를 부르지 않는다 — 키가 번들에 들어가고 `guard.ts` 를 못 태운다.

`server/src/index.ts` 의 known path 목록과 라우팅 분기에 `/reason` 을 **명시적으로** 추가한다. 빠뜨리면 마지막 분기가 `/extract` 처리라 엉뚱한 프롬프트로 흘러간다 (`index.ts:127,166`).

앱 쪽은 `intentClient.ts` 와 같은 모양의 얇은 클라이언트다. 실패하면 **판단 없음**으로 떨어진다.

### 언제 부르나

`RESULT` 를 낸 **뒤에** 부른다. 계획은 이미 화면에 있다.

**안 부르는 경우:** 옵션이 2개 미만, 또는 `comfortOrder` 가 `null` 이고 트렌드 스왑도 없을 때. 설명할 선택이 없으면 돈이 안 나간다.

### 입력 계약 — `parseReasonRequest`

입력 검증이 없으면 방어선이 아니다. `server/src/schema.ts` 에 파서를 둔다.

| 필드 | 검증 |
|---|---|
| `text` | 문자열, 500자로 자른다 (`/extract` 와 같은 값) |
| `mode` | `car`·`transit`·`walk` enum. 그 밖이면 거부 |
| `options` | 배열, **2~4개**. 미만·초과 거부 |
| `options[].key` | `planKey` 문자열(`후보id>후보id`), 64자×방문수 상한, 중복 거부 |
| `options[].stops` | 장소명 배열, **최대 6개**, 각 40자로 자른다 |
| `options[].totalMin` | 유한한 수, `0 < n < 1440` |
| 전체 바디 | 8KB 초과 거부 |

**`i` 같은 클라이언트 인덱스는 받지 않는다.** 서버가 `options` 순서대로 인덱스를 매기고, 응답도 그 인덱스로 받는다. 클라이언트가 준 번호를 되돌려주면 그게 곧 신뢰다.

마감 위반·폐점·`timingSource` 가 추정인 옵션은 **호출 전에 코드가 제외한다.** LLM 이 못 고르게 하는 편이 고른 뒤 막는 것보다 싸다.

`mode` 는 반드시 넣는다. 지하철인지 차인지 모르면 편의 판단이 성립하지 않는다. 지금 `/extract` 요청에도 모드가 안 실린다 (`intentClient.ts:98`) — 이건 `/reason` 에만 넣는다.

### 출력 계약 — `parseReasonResponse`

```json
{ "pick": 1, "why": "장 본 걸 들고 약국에 들어가지 않아도 돼요" }
```

| 검증 | 실패하면 |
|---|---|
| `pick` 이 정수, `0 ≤ pick < options.length` | **판단 없음** |
| `why` 가 문자열, 공백 제거 후 비어 있지 않음 | 판단 없음 |
| `why` 에 개행·제어문자 없음 | 제거 |
| **`why` 에 숫자가 없음** | **판단 없음** |
| `why` 60자 | 자른다 |

**숫자를 막는 이유:** 시간·거리는 코드가 잰다(AGENTS.md). `why` 에 "12분"이 들어오면 그건 LLM 이 만든 숫자이고, 화면의 `+12분` 과 어긋나는 순간 둘 다 못 믿게 된다. 추가시간은 코드가 `deltaMin` 으로 따로 붙인다.

`why` 를 `reasonCode` enum 으로 구조화하자는 제안은 받지 않는다. 그건 규칙 어휘를 다시 관리하는 길이고, 정형화 안 된 상황을 못 담는다 — 이 설계가 LLM 을 쓰는 이유가 그것이다. 대신 **숫자 주장만** 막는다.

### guard

`PER_MIN` · `PER_MIN_IP` · `PER_DAY` **세 표 모두**에 `/reason` 을 넣는다. `PER_DAY` 에 없으면 `overDailyCap` 이 `cap === undefined` 로 **그냥 통과시킨다** (`guard.ts:124`).

값은 `/extract` 예산을 **쪼개서** 쓴다. 더하면 OpenAI 일일 비용이 두 배가 된다.

| | `/extract` | `/reason` |
|---|---|---|
| 기기당 분당 | 10 → 그대로 | 10 |
| IP당 분당 | 30 → 그대로 | 30 |
| **일일** | 1200 → **900** | **300** |

`/reason` 은 계획이 있어야 부를 수 있지만, 재계산·화면 재진입으로 `/extract` 보다 자주 불릴 수 있다. 그래서 별도 상한을 둔다.

## 늦게 온 판단을 어떻게 버리나

v1 의 가장 큰 구멍이다. 옵션 인덱스는 식별자가 아니다.

요청할 때 세 값을 같이 기억하고, 응답이 오면 **셋 다 일치할 때만** 적용한다.

| 값 | 무엇 |
|---|---|
| `planRunId` | 이 `runPlan` 실행의 id. `RESULT` 에 실어 상태에 남긴다 |
| `optionKeys` | 요청 당시 옵션들의 `planKey` 배열 (`select.ts:10` 이 이미 만든다) |
| `userTouched` | 그 사이 사용자가 옵션을 고르거나 매장을 바꿨는가 |

하나라도 어긋나면 **조용히 버린다.** 특히:

- 사용자가 이미 다른 안을 골랐다 → 버린다. 추천이 선택을 빼앗으면 안 된다.
- 재계산이 돌아 `RESULT` 가 새로 왔다 → `planRunId` 가 달라 버려진다.
- 트렌드 스왑이 option 0 의 `override` 를 바꿨다 (`runPlan.ts:369`) → `optionKeys` 가 달라 버려진다.

## 화면 — 자동으로 바꾸지 않는다

```
1안   40분   빠른 길                    ← 선택된 채 그대로
2안   52분   +12분  ⭐ 추천
             장 본 걸 들고 약국에 들어가지 않아도 돼요
```

**`selectedOptionIdx` 를 건드리지 않는다.** 배지와 문구만 붙인다.

v1 은 `pick` 으로 선택을 옮기려 했다. 그러면 2.5초 뒤에 경로·도착시각·지도가 스스로 바뀐다 — 사용자가 보고 있던 것이 말없이 달라지는, 이 설계가 고치려던 바로 그 문제다. 그리고 `overrides` 가 `optionIdx` 로 키를 잡고 있어(`planFlow.ts:133`) 엉뚱한 슬롯에 붙을 수 있다.

`+12분` 은 코드가 계산한다. LLM 이 만든 숫자를 화면에 띄우는 일은 없다.

## 비용과 지연

| | |
|---|---|
| 비용 | 1콜 약 $0.01 (gpt-5.6-terra, 2026-09-17 실측 $10.39/1000콜) |
| 지연 | 중앙 2.5초 · p90 6.3초 |
| 사용자가 기다리나 | **아니다** — 계획은 이미 떠 있고, 배지만 나중에 붙는다 |

`/enrich` 를 흉내내지 않는다. `/enrich` 는 플래너 **앞**에서 12초 예산 안에 도는 구조다. `/reason` 은 `RESULT` **뒤**라 예산 밖이고, 늦으면 그냥 안 붙는다.

클라이언트 타임아웃 10초. 서버가 먼저 끝나도록 OpenAI 호출에는 8초를 준다.

## 검증 순서

| 단계 | 무엇 | 비용 |
|---|---|---|
| 1 | 단위 테스트 — `comfortOrder`, 시드 예약, 컷 면제, 입출력 파서, 늦은 응답 폐기 | 0 |
| 2 | **codex** 로 판단 프롬프트를 다듬는다 | 0 (구독) |
| 3 | **앱 API 실측** — gpt-5.6-terra 반복 측정 | 과금 |

codex 는 codex 모델이라 terra 가 아니다. 2단계는 "프롬프트가 말이 되는가"를 공짜로 거르는 자리고, "terra 가 실제로 그렇게 하는가"는 3단계에서만 나온다.

### 흔들림 기준을 구현 전에 정한다

temperature 를 0 으로 못 내리는 모델이다(`index.ts:169-173`). 같은 입력에 추천이 뒤집힐 수 있다.

물성 태그는 흔들려도 `decideNear` 의 분기 순서가 흡수했다(2026-09-17 측정: 7건 중 5건 흡수). 여기에는 그런 완충재가 없다.

**대표 케이스 10개 × 5회** 를 재고, 다음을 넘으면 **기능을 내지 않는다**:

| 지표 | 상한 |
|---|---|
| `pick` 이 뒤집히는 케이스 비율 | 20% |
| `pick` 은 같은데 `why` 가 서로 모순되는 비율 | 20% |

1단계(태그가 후보를 살린다)는 결정적이므로 이 기준과 무관하게 남는다. **2단계만 되돌린다.**

같은 `planRunId` 안에서는 한 번만 부른다. 캐시는 넣지 않는다 — 한 번만 부르면 캐시가 막을 중복이 없고, 키를 잘못 잡으면(예: `requestKey`) 다른 옵션 배열에 옛 판단을 붙인다.

## 범위 밖

| | 왜 |
|---|---|
| **주차** | 데이터가 없다. `/enrich` 는 평점·리뷰수·영업시간만 가져온다. Places 의 `parkingOptions` 로 가져올 수는 있으나 FIELD_MASK·보강 단계·점수 반영이 줄줄이 붙는 별도 축이다 |
| **사용자 선택 보존** | `overrides` 를 사용자 것과 시스템 것으로 가르는 별도 작업. 지금은 트렌드 스왑이 같은 맵에 쓴다 (`runPlan.ts:369`) |
| **편집 후 동선 재검토** | `usePlanRequest.ts:26` 이 `order: 'auto'` 를 하드코딩한다. 전체 재계산을 붙이면 사용자가 드래그한 순서를 먹는다 |
| **트렌드 스왑 이유 표시** | 같은 `/reason` 으로 붙일 수 있지만, 먼저 순서부터 맞힌다. 한 번에 둘을 하면 흔들림의 원인을 못 가른다 |

## 알려진 한계

- **경유지 4곳 이상**은 `enumerate.ts` 가 beam 으로 자른다. 편의 순열이 잘려 시드 예약이 실패할 수 있다. 그때는 예약이 없던 것처럼 동작한다.
- **`timingSource` 가 `estimate` 인 옵션**은 `/reason` 에 안 보낸다. 추정 위에서 편의를 판단하면 근거가 없다.
- **다중 턴**: `text` 는 마지막 사용자 문장만 쓴다. 여러 턴에 걸쳐 쌓인 선호는 못 본다. 전체 대화를 보내면 캐시 키와 개인정보 범위가 달라져 별도 결정이 필요하다.
- **`/reason` 도 인젝션 표면**이다. 사용자 문장이 들어간다. 출력이 정수 하나와 숫자 없는 60자 문자열이라 피해 범위가 좁고, 방어선은 `schema.ts` 다.

## 이 단계가 끝나면

`마트 → 약국 → 집` 이 옵션으로 고쳐지고(1단계), 왜 그게 있는지 화면에 보인다(2단계). 1단계는 LLM 과 무관하게 동작하므로, 2단계를 되돌려도 순서 문제는 고쳐진 채로 남는다.

남는 것은 **사용자 선택 보존**이다. 그건 다음 단계다.
