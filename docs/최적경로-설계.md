# 최적 경로 계산 — 설계 (v2, 2026-09-11)

Claude 초안(v1)을 Codex(gpt-5.6-sol)가 두 라운드 검토한 결과를 합친 것.
Codex 원문은 세션 스크래치에만 있고, 여기엔 채택한 것과 **기각한 것**을 같이 적는다.

## 한 줄 요약

**행렬(Matrix) API는 없다고 보고 설계한다.** 실측은 "직행 1회 + 전체 경로 R회"뿐이고,
그 응답의 구간(section)별 시간을 **재사용**해서 나머지 조합을 다시 채점한다.
"최적"이 아니라 **"검증한 후보 중 최선"**을 약속한다.

## 왜 행렬이 없나 (Codex가 정정한 API 사실)

| 공급자 | 되는 것 | 안 되는 것 |
|---|---|---|
| 카카오모빌리티 일반 키 | 자동차 길찾기 **경유지 ≤ 5**, 미래 길찾기(출발시각 지정, 경유지 ≤ 5), section별 duration/distance | 다중 목적지·다중 출발지·Matrix는 **제휴 승인 대상** |
| Google Routes | computeRoutes 경유지 ≤ 25, 요청당 과금 | computeRouteMatrix는 **요소당** 과금(20×20 = 400건). TRANSIT은 경유지 불가 |
| 카카오맵 / TMAP / ODsay 대중교통 | O-D 1:1 | 경유지 없음. ODsay 기본 탐색은 시간표 기반이 아님 |

v1이 "카카오 다중목적지 1→30이 싸다"고 가정한 게 틀렸다.

## 입력 / 출력

입력: `origin`, `destination`, `departAt`(기본 지금), `arriveBy?`, `mode`, `slots[]`
(각 슬롯: 검색 후보 `Kc=8`, `dwellMin`, `count`, `flexible`, `openNow`), `order: auto|locked`.

**V = Σcount** 가 실제 방문 수다. 경유지 제한·순열·호출 수 모두 V 기준. V ≤ 5.

출력: 옵션 Q=3 (후보 배정 + 순서 + totalMin + deltaMin + arriveBy 대비 여유),
슬롯별 대안 후보의 `addedMin`·`detourKm`(교체 시트가 소비), 슬롯별 `status`(아래 "못 찾았을 때"),
조건 완화안(있으면 별도 영역).

## 알고리즘

### 0. 직행 실측 (API 1) — LLM 추출과 병렬로 시작
O→D 1회. `directMin`, 폴리라인, `directKm`. 보정 계수는
**ρ = directMin / directKm** (경로 km 기준. v1의 haversine 기준은 기각).
mode·목적지가 LLM 출력에 달렸으면 car로 투기 호출하고 바뀌면 1회 버린다.

### 0.5 후보 검색 — 회랑에서 찾고, 없으면 넓힌다 (장소 API, 라우팅 API 0)
후보가 없으면 최적화할 게 없다. 검색은 한 점 주변이 아니라 **직행 회랑** 전체다.

- 직행 폴리라인을 따라 5개 점(0·25·50·75·100%)에서 반지름 r로 검색하고 place id로 합친다.
  카카오 로컬은 `x,y,radius`(최대 20km)·`sort=distance`, Google Places는 `locationRestriction` 사각형.
- 초기 r: 자동차 2km, 도보 500m, 대중교통 800m(역 주변).
- 슬롯의 `count`만큼(기본 1, 최소 Kc 확보가 목표) 못 찾으면 r을 2배씩 넓힌다. 상한은 둘 중 작은 것:
  `ρ`로 환산한 추정 우회가 arriveBy 여유를 넘지 않는 거리, 또는 절대 상한(자동차 15km, 도보 2km).
  arriveBy가 없으면 절대 상한만.
- 상한까지 넓혀도 없으면 **가장 가까운 곳 1~3개를 그대로 후보로 넣고** 실측한다. 판정은
  라우팅 결과로 코드가 한다("지금 출발해도 늦어요" 화면이 이미 있다). 검색이 아예 0건이면
  `ambiguous`로 되묻는다("경로 15km 안에 ○○이 없어요. 다른 곳으로 할까요?").
- 브랜드 지정(올리브영)과 종류 지정(빵집)은 같은 규칙이다. 브랜드는 대체 불가라 확대가
  더 자주 일어날 뿐이다. 종류 검색은 회랑 안에서 8개가 쉽게 차므로 확대가 드물다.
- 확대 검색으로 들어온 후보는 `detourKm`가 크게 나오므로 교체 시트의 거리 정렬이 그대로 드러낸다.

호출 수: 슬롯당 5회(회랑 점) + 확대 단계당 5회. 장소 API는 라우팅보다 싸고 쿼터가 넉넉하다
(카카오 로컬 일 10만 건). 확대는 병렬로 하지 말고 단계별로 — 대부분 첫 단계에서 끝난다.

### 1. 후보 정리 (API 0)
- `count` 확장, 같은 place id 중복 금지, `flexible=false`는 후보 1개로 고정.
- 삭제는 **확실한 것만**: 카테고리 오류, 확실한 휴무. 추정 시간으로는 지우지 않는다
  (추정치는 하한이 아니라서 진짜 최적을 지운다 — v1의 "여유 초과 삭제" 기각).
- 영업시간은 여기서 거르지 않는다. 누적 도착시각이 나온 뒤(4단계) 검사한다.

### 2. 추정 점수 (API 0)
직행 폴리라인에 후보를 투영해 진행도 `s∈[0,1]`, 부호 있는 수직거리 `y`를 얻는다
(`geo.ts`의 `crossTrack`이 이미 한다). 가상 좌표 `p = (s·L, y)`.

- 추정 leg 거리 `g(u,v) = |p(u)−p(v)| + 0.5·max(0, x(u)−x(v))` — 역주행 벌점
- `D_A` = Σg (corridor 기준), `D_B` = Σhaversine(leg), `D_C = 0.35·D_A + 0.65·D_B`
- 시간 = ρ × 거리 + Σdwell

V ≤ 3은 전수, V ≥ 4는 추정기별 beam 64. locked는 부분 순서 제약으로.

### 3. 1라운드 실측 (API R)
- **V = 1**: 후보 8개 **전부** 실측 (9회). 하루 3회 × 1명이면 27회/일. 정확한 top-3와
  정확한 대안 addedMin을 얻는다. 사용자가 늘면 그때 R=4로.
- **V ≥ 2**: R=4. `D_C` 상위 2 + `D_A` 1위 + `D_B` 1위, 중복이면 overlap 최저 안으로 채움.
- 반드시 병렬. 개별 타임아웃. 하나 실패해도 전체를 막지 않는다.

### 4. leg 재사용으로 전체 재채점 (API 0)
실측 응답의 section에서 leg 시간을 뽑아 캐시에 넣는다. 조합들은 leg를 공유하므로
(예: O→c1), 실측 leg는 실측값을, 없는 leg만 추정치를 써서 **전체 조합을 다시 채점**한다.
누적 도착시각으로 영업시간·dwell을 검사한다.

같은 leg를 다른 시각에 재사용하는 기준(자동차):

| 출발시각 차 | 처리 |
|---|---|
| ≤ 5분 | 그대로 |
| 5~15분 | 재채점에만 사용, 불확실성 `max(1분, 0.1×legMin)` 가산 |
| > 15분 | 미실측 취급 |

피크 경계를 넘거나 arriveBy 여유 < 5분이면 5분 이내라도 불확실성을 붙인다. 도보는 훨씬 넓게.

### 5. 2라운드 (API +2, 최대 +3) — 조건부
`μ = max(2분, 0.08×directMin)`. 다음 중 하나면 2회 추가:
- 3분 이상인 실측 leg에서 `max(t/t̂, t̂/t) > 1.6` (추정기가 이 동네에서 틀린다)
- 전체 leg WAPE `Σ|t−t̂| / Σt > 0.25`
- 미실측 leg가 1개뿐인 도전자가 실측 3위보다 μ 이내
- 도착 예정이 `arriveBy ± μ`

추가 대상은 "미실측 leg 1개인 예상 상위 2개". 없으면 2개 이하. 비율 > 2.0, WAPE > 0.4,
유효 실측안 < 3이면 **새 leg를 가장 많이 재는 탐색안** 1개를 더 붙인다(상위안이 아니라).

### 6. Q=3 선택 — 다양성은 실측 후에
- 허용 범위 `Δmax = clamp(0.15×directMin, 2, 8)`분. 직행 20분이면 3분
  (v1/Codex 1라운드의 "10분 이내"는 짧은 경로에 너무 느슨해 기각).
- 1안 = 최단. 이후 `score(p|S) = T_p + max_{q∈S}(0.6·Δmax·J_C + 0.4·Δmax·J_O)`
  최소를 반복 선택. J_C = 후보 집합 Jaccard, J_O = 방향성 leg 집합 Jaccard.
- 3개가 안 나오면 억지로 만들지 않는다.
- ~~**"경유지 하나 뺀 안"은 옵션이 아니라 조건 완화안.** arriveBy 위반일 때 별도 영역에.~~ **2026-09-11 제거.** 무엇을 뺄지는 사용자가 판단할 항목이라 계획기가 고르지 않는다(실측 1회 절약). 화면은 늦을 때 경유지마다 "빼면 언제 도착"만 보인다. 3안 선택도 같은 날 화면에서 뺐다(계획기는 여전히 3안을 만들지만 1안만 쓴다).

### 7. 확정 시 dwell 반영 (API +1~2, 1안만)
전체 경로 API는 중간에 20분 머문다는 걸 모른다. 총 dwell ≥ 15분이면 확정된 1안만
긴 dwell 지점에서 끊어 **미래 길찾기**(출발 = 도착 + dwell)로 뒷부분을 재실측한다.
1라운드에서는 "교통 변화 위험" 표시만.

## 못 찾았을 때 — 제품 규칙

알고리즘이 아니라 제품 규칙이다. 원칙 둘:

- **조용히 빼지 않는다.** 사용자가 말한 경유지는 결과 화면에 반드시 흔적이 남는다. 칩이 그 자리다.
- **경유지 하나 때문에 계획 전체를 막지 않는다.** 나머지로 계획을 세우고 문제 경유지만 상태를 단다.
  매번 되물으면 "3초 안에 답"과 충돌한다.

플래너는 슬롯마다 `status`를 돌려주고, 칩과 추천 화면이 그린다. 판정은 LLM이 아니라 플래너가 한다.

| status | 상황 | 앱이 하는 것 | 칩 | 선택지 |
|---|---|---|---|---|
| `far` | 회랑·확대 상한 안엔 없고 더 멀리엔 있음 | 가장 가까운 곳으로 계획, "+M분 돌아감" 강조 | 멀리 있음 | 그대로 / 빼기 / 다른 종류로 |
| `none` | 0건 | 그 슬롯만 비우고 나머지로 계획 + `ambiguous` 되묻기 | 못 찾음 | 검색어 고치기 / 빼기 |
| `closed` | 있지만 도착 시 전부 마감 | 계획은 세우되 경고. 확대 범위에 열린 곳이 있으면 대안 제시 | 마감 | 빼기 / 대안으로 교체 / 그래도 감 |
| `late` | 들르면 arriveBy 불가 | "지금 출발해도 늦어요" + 조건 완화안("이 경유지 빼면 N분 여유") | 늦음 | 빼기 / 마감 조정 / 그래도 감 |
| `short` | count 부족(3곳 중 2곳) | 찾은 만큼으로 계획 | 2/3곳 | 그대로 / 더 넓게 |
| `ok` | — | — | — | — |

되묻기는 `none`일 때만. 검색어 자체가 쓸 수 없을 때(오타·지역에 없는 브랜드)는 계획을 세워도
의미가 없다. 나머지는 계획을 먼저 보여주고 칩에서 고치게 한다.

미정: `far`의 절대 상한(15km는 임시값). "그래도 감"을 고른 뒤 도착 알림 문구를 바꿀지.

## 3초 파이프라인 (p95 기준)

```
0.0  LLM 추출 시작 ─┐  직행 실측 시작(car 투기)
1.5  추출 끝        │  회랑 검색 슬롯별·5점 병렬 (0.3, 확대 시 +0.3/단계)
1.8  후보 정리 · 추정 채점 (로컬, ms)
1.9  R회 병렬 실측 (0.5)
2.4  1라운드 수집 마감 → 재채점
2.6  최초 응답 확정 (검증된 3안이 있으면 3안, 아니면 1안 먼저)
2.9  2라운드가 끝났으면 포함, 아니면 백그라운드 갱신
```

2라운드에서 새 1위가 나와도 `max(2분, 5%)` 이상 좋아질 때만 자동 승격(화면 흔들림 방지).

## 대중교통

경유지 경로가 없어 조합당 V+1회 **순차**(다음 구간 출발 = 이전 도착 + dwell).
3안 완전 검증은 `1 + 3(V+1)`회 = V=1..5에서 7·10·13·16·19회. 3초 안엔 무리.

v1 범위: 후보는 corridor 진행도·수직거리로 고르고, 순서는 진행도 순(또는 locked),
**1안만** 순차 실측해 보여주고 나머지는 "계산 중"으로 갱신. 시간표 기반 정확성은
공급자 문제(ODsay 기본 탐색은 정적)라 지금은 얻을 수 없다.

## 캐시

키: `(place id 또는 좌표 5자리, 방향, provider, mode, 출발 15분 버킷)`. 좌표 3자리(≈100m)는
도로 반대편·역 출구를 합쳐 버려서 기각. TTL은 자동차 5~10분, 도보 길게, 대중교통 매우 짧게.
arriveBy 여유 < 5분이면 2분 넘은 캐시는 재검증. 목 데이터의 `legs` 테이블이 이 캐시의 원형이다.

## 어디서 도는가

- **조합·추정·재채점·선택은 앱의 순수 TS 모듈** (`src/lib/routePlan/`). 공급자를
  인터페이스로 두고 haversine 목 공급자로 node 테스트가 돌아야 한다.
- **API 호출은 Workers 프록시** (`/route`). 키를 가리고 rate limit. LLM `/extract`와 같은 구조.
- 판정("지금 출발해도 늦어요")은 지금처럼 앱에. 나중에 지연이 문제면 플래너 전체를
  Workers로 옮길 수 있게 모듈 경계를 지킨다.

## 남은 위험 (해결 안 됨)

- 어떤 휴리스틱도 행렬 없이는 global top-3를 보장 못 한다. 화면 문구도 "검증한 안 중 최선".
- ETA는 확률값. 도착 보장 문구는 `ETA + 버퍼`로. 버퍼 크기는 미정.
- 주차·하차·건물 입구 도보는 도로 API에 없다. dwell과 별도의 접근 버퍼가 필요. 미정.
- 카카오 일반 키 일일 무료 쿼터를 아직 확인 안 했다. **구현 전에 확인.**
- 429·부분 실패 시 "도착 가능"을 단정하지 않고 신뢰도 낮음으로 표시. UI 미정.

## Codex 제안 중 기각한 것

- 추정기 A/B/C **각각** K-best DP 32개 → 합집합. V ≤ 3은 전수가 더 단순하고 같은 결과. V ≥ 4만 beam.
- 1라운드 컷 "최선 대비 10분" → 상대값 Δmax로 교체(2라운드에서 Codex도 동의).
